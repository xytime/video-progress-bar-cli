# 架构白蓝白红博弈推演（Adversarial Architecture Review）

## 规则说明

本文档对《系统架构审查与改进报告》的核心结论做**对抗式压力测试**，每个"战役"四角色轮转：

- ⚪ **白·命题/质询/裁决**（中立裁判）：框定争点、追问双方、最终裁决并给行动项与定级。
- 🔵 **蓝·防守**（现状辩护方）：以**最强**理由为现有设计辩护（steelman，不是稻草人）。
- 🔴 **红·进攻**（攻击方）：给出**具体可复现**的失效场景、攻击路径、最坏情况。

裁决定级：🔴P0 立即 / 🟠P1 一月 / 🟡P2 季度 / 🟢保持现状。

> 设计意图：很多"缺陷"其实有合理由来。只有让蓝队把理由说足、红队把刀亮真，白队的裁决才有价值。

## 战役一：cron 贫环境 vs 隐式富环境假设 ⭐（主战役）

### ⚪ 白·命题
关键子进程（`yt-dlp`、解 n-sig 用的 `deno`）依赖运行环境的 PATH。cron 用 `.venv/bin/python` 直跑脚本时**不激活 venv**，PATH 为最小集（`/usr/bin:/bin`），既无 `.venv/bin` 也无 `/opt/homebrew/bin`。争点：这是"运维配置问题"还是"架构缺陷"？

### 🔵 蓝·防守
- 这是经典 Unix 实践：可执行文件理应在 PATH 上；cron 环境贫瘠是**众所周知**的，运维补一行 `PATH=` 即可，不该让应用代码替运维兜底。
- 应用代码保持环境无关、可移植；硬编码 `/opt/homebrew/bin` 反而把 macOS/Apple-Silicon 细节焊进业务，换机即坏。
- 当前 dashboard 富环境长期跑得好好的，证明设计本身没问题，只是某次 cron 配置漂移。

### ⚪ 白·质询
- 事实：同一类根因在**三个不同位置**各炸一次（发现裸 `yt-dlp`、下载缺 `deno`、历史 `.env` 相对路径），跨越数月、由不同作者写就。**一个"运维配置问题"会反复以不同形态复发吗？** 还是说，代码里存在一个系统性的"假设富环境"的坏习惯？
- 事实：富环境(dashboard)的存在**掩盖**了贫环境(cron)的失败——"手动能跑、定时静默挂"，这正是它潜伏 1555 次仍无人知的原因。

### 🔴 红·进攻
- **复现**：`env -i HOME=$HOME PATH=/usr/bin:/bin .venv/bin/python -c "import subprocess; subprocess.run(['yt-dlp','--version'])"` → `FileNotFoundError`。同理 `deno` 缺失 → `n challenge solving failed` → 全部格式失效。两者今日均已实测复现。
- **蓝队的"补 PATH= 一行"恰恰是反例**：它把正确性外包给一个**不在版本控制、与同机 Futu 任务共用、易漂移**的 crontab 文件。今天能跑不代表明天——homebrew 路径变更、机器迁移、用户改 crontab，都会让它再炸，而且**依旧静默**。
- **更深的攻击**：今日只修了发现与下载两条路径。**上传(`wechat_uploader`)、`cli.main` 字幕、`cover_generator`** 仍走隐式环境。下一次 cron 触发这些路径时，同样的刀会从新角度捅进来。

### ⚖️ 白·裁决 —— 🔴 P0｜判：架构缺陷，非纯运维
红队胜。"反复以不同形态复发"是抽象泄漏的铁证，不是配置漂移。但蓝队的"勿硬编码 macOS 细节"是有效约束——故裁决**不是**到处硬写路径，而是：
- **建立运行环境 SSOT**：`settings.build_subprocess_env()` / `settings.tool_path(name)` 用 `shutil.which` + 已知候选目录（可配置、带 macOS/Linux 分支）解析，集中一处、可测试、可移植。
- **全量收口**：所有外部命令调用一律经它，禁止裸调。
- **启动自检 fail-fast + 告警**：缺工具立即显式失败，杜绝静默。
- crontab `PATH=` 仅作**纵深防御**第二层，不作唯一防线。

## 战役二：微信单账号会话 = 发布唯一出口 SPOF

### ⚪ 白·命题
所有发布经由单个微信视频号账号的 Playwright 会话（`wechat_state.json`）。会话过期即全链路发布停摆。今早实发：2 条高分视频卡 `LOGIN_REQUIRED`。

### 🔵 蓝·防守
- 视频号**本质上**就是单账号实体：一个内容品牌对应一个号，这不是技术选择而是业务事实。"多账号轮转"在合规上可能违反平台规则（矩阵号、内容搬运被判违规），盲目引入是**用合规风险换可用性**。
- 已有 keepalive 看门狗定期刷新会话、有 LOGIN_REQUIRED 状态 + Telegram 推 QR、有 UNCONFIRMED 专项保护（不误删产物）。**故障是可恢复的人工介入，不是数据丢失**。
- 单账号让"原创"标记、粉丝信任、算法权重得以积累——这正是业务价值所在。

### ⚪ 白·质询
- 接受"单账号是业务事实"。但争点其实不是"要不要多账号"，而是：**会话失效是否被尽早、可靠地发现并恢复？**
- 事实：keepalive **默认需手工启用**（`WECHAT_KEEPALIVE_ENABLED` 默认 False），无启动自检。若忘开，会话静默老化直到过期。
- 事实：告警是**失效后**才发（已经卡 LOGIN_REQUIRED 才推 QR），而非**失效前**预警。今早就是事后才发现。

### 🔴 红·进攻
- **最坏场景**：keepalive 没开 + 管理员夜间不在线 → 会话过期 → 当晚及次日所有高分视频卡 `LOGIN_REQUIRED` → 热点视频错过黄金发布窗口（时效性内容直接作废）。今早已是此剧本的轻量版。
- **QR 时效攻击**：QR 仅几分钟有效。若告警链路慢（bot 掉线、管理员错过），QR 过期需重发，恢复被进一步拖延。
- **会话明文**：`wechat_state.json` 明文存 cookie，泄露即被劫持发布权——单账号的"鸡蛋"全在这一个明文篮子里。

### ⚖️ 白·裁决 —— 🔴 P0（可用性）+ 🟡 P2（安全）｜判：保留单账号，强化韧性
蓝队赢"保留单账号"，红队赢"恢复机制不足"。行动项：
1. **keepalive 默认开 + 启动自检**（缺则告警）。
2. **会话健康预测**：估算剩余有效期，**失效前**主动预警，把"事后救火"变"事前补登"。
3. **QR 恢复链路加固**：QR 推送多通道（Telegram + 仪表盘 + 本对话），附剩余时效与一键重发。
4. （P2）`wechat_state.json` 加密 + 权限 640。
5. 暂**不**引入多账号轮转（合规风险 > 收益），但在风险登记中标注"发布出口无冗余"。

## 战役三：外置卷 `/Volumes/EXT2T` 承载 DB + 全部产物

### ⚪ 白·命题
SQLite DB（WAL）与全部视频产物都在外置卷 `/Volumes/EXT2T`。卷掉线 → DB 锁异常、WAL 堆积、全业务中断。

### 🔵 蓝·防守
- 视频产物动辄数十 GB，本机 SSD 放不下，外置大容量卷是**务实选择**。
- Thunderbolt/USB 外置卷在桌面常驻场景稳定性足够；至今未发生卷掉线事故，是**理论风险非现实风险**。
- DB 与产物同卷，路径关系简单、备份一致（一个卷一起备），分离反而增加"DB 指向已卸载卷上产物"的不一致风险。

### ⚪ 白·质询
- 产物放外置卷无争议。但 **DB（含锁、WAL）放外置卷**与产物放外置卷是**两件事**——DB 体积小、却是全系统的"真相中枢"和并发锁所在。
- SQLite 的 WAL/锁在网络/可移除文件系统上有**已知的可靠性弱点**（fsync 语义、锁字节范围在某些 FS 上不可靠）。

### 🔴 红·进攻
- **复现路径**：卷在写入中途断开（线松动、休眠唤醒、供电波动）→ `-wal` 未 checkpoint → 重挂后 SQLite 可能报 `database disk image is malformed` 或锁死 → 所有触发器（cron + dashboard）同时失败，且因 §战役五的静默失败而**无告警**。
- **放大效应**：DB 一坏，不只发布停，连"哪些视频处理到哪一步"的状态都丢——断点续跑失去依据，可能重复下载/重复发布。
- "至今没出事"是**幸存者偏差**，不是可靠性证明。

### ⚖️ 白·裁决 —— 🟠 P1｜判：DB 迁本机 SSD，产物留外置卷
红队胜在"DB ≠ 产物"。行动项：
- `pipeline.db` 迁本机 SSD（小体积，安全收益大）；产物目录仍指向外置卷。
- 增加**卷健康探测**：路径不可达立即告警 + 暂停调度（而非静默失败）。
- 定期 `wal_checkpoint(RESTART)` 收敛 WAL。

## 战役四：Dashboard 单进程托管全部调度

### ⚪ 白·命题
秒级队列调度、keepalive、发现/处理触发，全挂在一个 FastAPI 进程的 daemon 线程上。进程退出 = 自动化全停，无自愈。

### 🔵 蓝·防守
- 单进程 = 简单。daemon 线程共享内存，零 IPC 开销，调试直观。对一个**单机、单人运维**的系统，引入 Redis/RabbitMQ/多服务是**过度工程**。
- 有 cron 作为**第二条腿**：即便 dashboard 挂了，09:00/21:00 的 cron 仍会跑评分+发布，业务不会完全归零。
- `@reboot vpanel ui start` 保证重启自拉起。

### ⚪ 白·质询
- "cron 第二条腿"恰恰是双刃：它提供了冗余，**也**正是战役一里"富/贫环境双触发掩盖 bug"的来源。
- `@reboot` 只覆盖"机器重启"，不覆盖"进程自己 crash/OOM/被误杀"——后者无自愈。

### 🔴 红·进攻
- **复现**：dashboard 进程因某子线程未捕获异常、或外置卷卡顿导致的阻塞、或 OOM 被系统杀 → 三个调度线程同时静默死亡 → 秒级队列不再触发、keepalive 停转（会话开始老化，埋下战役二的雷）→ 直到管理员**偶然**发现。
- cron 第二条腿当前**自身就有病**（战役一的贫环境 bug），所以"dashboard 挂了还有 cron"在今日语境下是**两条都瘸的腿**。

### ⚖️ 白·裁决 —— 🟠 P1｜判：调度需要被守护，但不必上消息队列
蓝队赢"勿过度工程（不上 MQ）"，红队赢"单进程无自愈"。行动项：
- 用 **launchd/supervisor 守护 dashboard**：crash 自动重启（KeepAlive=true），覆盖非重启型退出。
- 调度线程加**心跳自检**：线程死亡可被外部探测并告警。
- 先修好 cron 这条腿（战役一），让"双腿冗余"名副其实。
- 暂不引入 MQ。

## 战役五：静默失败 vs 可观测性 ⭐

### ⚪ 白·命题
失败常被伪装成"正常空结果"：发现 yt-dlp 失败→返回空→调度器当"无新视频"。1555 次失败零告警，潜伏数天。

### 🔵 蓝·防守
- "宽容失败、继续运行"是**有意的韧性设计**：单频道超时不该让整轮发现崩溃，返回空让流程优雅继续。
- 系统已有 Telegram 告警与仪表盘，不是全黑盒。
- 加太多告警会**告警疲劳**，反而让真问题被淹没。

### ⚪ 白·质询
- "宽容单点失败"对 ✓。但"宽容"与"分不清失败和空结果"是两回事——前者是韧性，后者是**可观测性盲区**。
- 现有告警覆盖的是"已进入管线的视频"的失败，**没有**覆盖"管线入口（发现）整体停摆"。1555 次失败正发生在这个盲区。

### 🔴 红·进攻
- **这正是本次事故的传播链**：发现静默挂 → 漏斗顶端枯竭 → 数天后人工从"发布变少"反推 → 才发现爬虫早已全灭。**从故障发生到被发现，延迟以"天"计。**
- 告警疲劳是真问题，但**漏报**比**误报**致命得多。当前是"零告警导致漏报"，不是"告警太多"。
- 反例攻击：若某天 cookie 真失效 / 代理全挂 / 卷掉线，**同样会以空结果静默通过**——盲区是通用的，不止发现这一处。

### ⚖️ 白·裁决 —— 🔴 P0｜判：区分"失败"与"空"，建漏斗心跳
红队完胜。行动项：
1. 每个外部调用边界**检查 returncode**，"非空≠成功、空≠正常"，失败必发 Telegram。
2. **漏斗心跳表**：每日发现数/过门数/发布数/各状态计数落库；**连续 N 小时无新发现 或 无 PUBLISHED → 自动告警**。
3. 告警**分级**（致命/警告/信息）以防疲劳，但底线是"整体停摆必须可见"。

## 战役六：yt-dlp / YouTube 依赖韧性与 cookie

### ⚪ 白·命题
下载与发现强依赖 yt-dlp + cookie + deno 解 n-sig。YouTube 频繁变更（格式门控、PO-token、n-sig），cookie 会失效。

### 🔵 蓝·防守
- yt-dlp 是事实标准，已有诸多韧性：H.264 优先规避 AV1 SIGSEGV、`--remote-components ejs:github` 解 n-sig、curl 外部下载器 10 次重试断点续传、动态代理 + 日本节点提速、cookie 文件优先于浏览器导出、exit 101 退避重试。
- 这些都是**真金白银的实战补丁**，证明依赖被认真对待。

### ⚪ 白·质询
- 韧性补丁确实丰富。但它们都是**被动**的（出事后加），且高度依赖"yt-dlp 够新 + deno 在 PATH + cookie 没过期"三个隐含前提同时成立。
- 今日实证：yt-dlp 旧版 + 缺 deno，三前提塌两个，全部下载即失败。

### 🔴 红·进攻
- **cookie 慢性病**：cookie 无 TTL、手工维护。失效后系统仍对同一坏 cookie **重试 10 次**——把"快速失败"做成了"缓慢失败"，浪费时间还触发更多 bot-check。
- **版本滞后必复发**：YouTube 每隔数月变招，yt-dlp 旧版必再出 `format not available`。今日升级只是把炸弹定时器**重置**，没拆除。无"版本新鲜度探测"。
- **n-sig 链脆**：`ejs:github` 需联网拉 GitHub 上的解算器 + 本地 deno。GitHub 不可达 / deno 缺失 / 解算器协议再变，任一断点即全失败，且（战役五）静默。

### ⚖️ 白·裁决 —— 🟠 P1｜判：把被动补丁升级为主动健康管理
双方各有理。行动项：
- **cookie 健康探测 + 快速熔断**：失败 2 次即验 cookie 有效性，无效则标记 + 触发刷新，**停止对坏 cookie 的无效重试**。
- **yt-dlp 版本新鲜度探测**：超过 N 天告警提示升级（把"定时炸弹"变"可见仪表"）。
- 发现路径已加 `--ignore-no-formats-error`（元数据不需格式）——保持。
- n-sig 依赖链纳入启动自检（deno 可达？）。

## 战役七：评分悬崖 + dateafter = 发布漏斗自我饿死 ⭐（工程 vs 产品）

### ⚪ 白·命题
`compute_auto_score` 是二元悬崖（过门 80–95 / 没过 ≤70，71–79 空档），叠加 `--dateafter now-3days` 只取新片。"够新"与"够热"交集极小 → 可发布候选周期性归零。

### 🔵 蓝·防守
- 两个设计都有**明确产品理由**：dateafter 3 天是为规避"历史高赞霸榜、刷不出新内容"（v1.5.0/1.7.0 的真实问题）；热度门槛是为**只发已验证会火的内容**，保证视频号调权与质量。
- 悬崖式门槛是**有意的质量闸**：宁可少发，不发没验证过的投机内容。71–79 空档是"既不够热、也不值得发"的灰色地带，砍掉是特性不是 bug。
- 阈值已从 (2000,3.5%) 下调到 (1500,3.0%) 缓解过断流——说明已在调。

### ⚪ 白·质询
- 蓝队的产品逻辑成立。但**自洽不等于最优**：当"够新(3天)"与"够热(>1500&>3%)"几乎不相交时，闸门事实上把自己关死了——这不是"严格质量",是"漏斗饿死"。
- 数据：近日 AUTO 候选大量集中在 <60 分、75+ 几乎为零（即便发现端修好后，热度门槛仍是出口瓶颈）。

### 🔴 红·进攻
- **悬崖的脆性**：一批 1500–1600 views、3.0–3.2% 点赞率的视频会因评分恰好卡在门槛两侧而剧烈抖动——发布量对噪声敏感，今天 8 条明天 0 条，不可预测。
- **新片悖论**：3 天内的视频**物理上**来不及攒够 1500 views & 3% 赞率（除非本就病毒级）。于是系统专门去发"刚发布、还没验证"的片子，**与"只发验证过的内容"的初衷自相矛盾**。
- 结果：既没达成"高质量"（抢发未验证），也没达成"稳定数量"（漏斗饿死）。

### ⚖️ 白·裁决 —— 🟠 P1｜判：属产品参数，需人决策；工程提供可调旋钮与数据
这是**产品权衡**，非纯工程对错，白队不替产品拍板，但给出结构化选项：
- **选项A**：dateafter 放宽到 7 天（让有热度沉淀的片进入），代价是内容稍旧。
- **选项B**：评分曲线加 71–79 线性过渡区，消除悬崖抖动。
- **选项C**：频道轮询（AUTO 源）与关键词高赞发现采用**不同时窗**（轮询可更长）。
- **选项D**：维持现状，接受低量高确定性。
- **建议**：A+B 组合，并用心跳表观测前后"发现数/过门数/发布数"对比再固化。**决策权在用户**。

## 战役八：安全面（会话明文 / API 无鉴权 / 密钥明文）

### ⚪ 白·命题
`wechat_state.json` 明文存登录 cookie；Web 仪表盘 API 多为无鉴权强触发端点；Clash secret / TG token 明文 env。

### 🔵 蓝·防守
- 部署形态是**单机、内网、单人**，监听虽 `0.0.0.0:9100` 但处于家庭/工作室内网，攻击面有限。
- 加密、鉴权、密钥轮转对单人系统是**运维负担 > 收益**；Telegram bot 侧已是 Fail-Closed 强鉴权（非管理员不响应）。

### ⚪ 白·质询
- 内网假设依赖"网络边界可信"。`0.0.0.0` 监听 + 同机还跑**实盘交易系统(Futu)** → 一旦内网有任一被攻陷的设备（IoT、访客手机、被钓鱼的浏览器），横向移动门槛极低。
- 同机有金融系统，抬高了"被当跳板"的价值。

### 🔴 红·进攻
- **横向移动**：内网任一设备失陷 → 访问 `http://<host>:9100` 无鉴权触发管线/删视频/改优先级；读 `wechat_state.json` 明文 cookie → **劫持视频号发布权**（可发任意内容到你的号，声誉/合规灾难）。
- **密钥拾取**：拿到 Clash secret 可接管代理（窥探/改写同机所有出网流量，含 Futu？需评估）；TG token 可冒充 bot。
- 单人系统不等于无攻击面——它等于"无人盯防的攻击面"。

### ⚖️ 白·裁决 —— 🟡 P2（局部 P1）｜判：纳入风险登记，做最小加固
内网假设降低**紧迫性**但不消除**后果严重性**（同机金融系统抬高赌注）。行动项：
- （P1 小工）仪表盘绑 `127.0.0.1` 而非 `0.0.0.0`（若无需局域网访问），或加一层最小 token。
- （P2）`wechat_state.json` 加密 + 权限 640；密钥纳入轮转计划。
- 在风险登记表显式记录"同机金融系统 → 提高内网安全基线"。

## 元结论

八场博弈中，**三场判 P0**（环境脆弱性、发布出口 SPOF、静默失败），且**彼此咬合成一条致命链**：

> 环境脆弱性(战役一)制造故障 → 静默失败(战役五)让故障潜伏 → 当故障最终撞上某个 SPOF(战役二/三/四)时，已是**无预警的全面停摆**。

这条链正是本次"发布骤降"的完整剧本。**先打掉"静默"（让故障可见），再补"环境 SSOT"（让故障不发生），SPOF 的韧性改造可随后跟进**——这是性价比最高的施工顺序。
