## 2. 当前发布规则

### 2.1 发现与重算

- `monitor_channels.py` 每 30 分钟发现频道新视频，写入 `processed_videos`。
- `source='DISCOVERY'` 的视频只用于浏览和高赞页，不进入自动评分/自动发布。
- `rescore_refresh.py` 当前每 3 小时运行一次，用最新播放量重新计算分数，捞回后涨起来的视频。

### 2.2 自动入选

- 普通视频自动发布线为 `score >= 75`。
- 演讲/TED/高校类频道可使用较低线：`speech_publish_score_line=40`，由 `speech_channel_ids` 识别。
- `channel_score_floors` 可对指定频道做评分托底；这只影响评分或频道策略，不绕过 P0/P1/P2 安全审查。
- 黑名单视频、黑名单频道不应进入高分待发布队列。

### 2.3 时间门禁

- `settings.is_public_publish_window()` 是公开视频提交的统一时间门禁。
- `PipelineManager._is_public_publish_window()` 用它保护视频号、抖音、快手的新片同步、补发、历史迁移。
- 审核回查是只读动作，原则上不受发布窗口限制。
- 美股盘中重负载保护仍独立存在：ET 09:15-16:15 工作日不启动新重活，保护同机交易数据链路。

### 2.4 主流水线

`PipelineManager.run_daily_job()` 当前顺序是：

1. 对 `PENDING` 视频评分。
2. 拉取高分待发布视频，最多批量循环处理。
3. 加工链路：下载、文案、转写/翻译/字幕、竖屏渲染、封面、安全审查。
4. 视频号投递。
5. 视频号延迟补发。
6. 快手回查/新片重试，前提是快手开关开启。
7. 抖音回查、新片同步、历史迁移，前提是抖音开关开启。

### 2.5 视频号规则

- 视频号是主发布平台。
- 投递前必须在发布窗口内。
- 投递前必须有专门生成封面证明；不能把视频截图或默认封面当作有效封面。
- 上传器 `exit 2` 代表登录态失效，流水线置 `LOGIN_REQUIRED`。
- 上传器 `exit 3` 代表发布结果无法确认，流水线置 `FAILED` 并保留产物，不置 `PUBLISHED`，不 GC，不自动重发。
- 只有上传器确认成功后，本地 `processed_videos.status` 才写 `PUBLISHED`。
- 仍要区分：本地 `PUBLISHED` 是流水线账本成功，不等于已截图证明平台作品卡片可见。

### 2.6 抖音规则

- 当前抖音开关开启。
- 视频号发布后，同一成片会进入抖音 NEW 同步逻辑。
- 抖音上传成功只代表提交被平台接受；作品管理页明确确认后才可记最终 `PUBLISHED`。
- `UNDER_REVIEW`、`UNCERTAIN`、`PUBLISHED` 必须分开，不能把审核中或无法校准当成功。
- 上传前要重查标题、文案、字幕、封面、自主声明；失败时熔断本轮抖音动作。
- 当前本地账本快照：`UNCERTAIN NEW=72`、`UNDER_REVIEW HISTORY=19`、`PUBLISHED NEW=8`、`PUBLISHED HISTORY=9`。这说明抖音侧最需要单独治理“待人工核验/回查校准”队列。

### 2.7 快手规则

- 当前快手开关关闭。
- 代码仍保留快手新片同步、历史迁移、审核回查规则，但不会执行公开投递。
- crontab 仍有 19:40 快手历史迁移入口；因开关关闭和限额为 0，当前实际无公开发布作用。

### 2.8 普通话配音再制规则

- 配音任务是独立域，不由日常调度、评分、发布窗口、历史补发自动领取。
- 配音版发布必须人工确认，且拥有独立平台投递与确认记录。
- 原视频 `PUBLISHED` 不能证明配音版也发布成功。

## 3. 今天暴露出的机制问题

1. 规则源多头：代码默认、`.env`、旧调研文档、crontab 注释、每日工单文档不完全一致。
2. 窗口和执行器没有自动核对：没人每天证明“每个有效发布窗口至少有一个执行者，且执行点落在窗口内”。
3. 早窗只有单次触发，不是窗口内巡航：`06:35` 之后出现的新高分候选会错过早窗。
4. 日报不是执行者：`daily_ops_report.py` 只读，且 09:00 才报，无法主动挽救 06:30-09:00 早窗。
5. crontab 是当前事实源之一，但不在 Git 中自动审计；注释漂移后很难从代码评审发现问题。
6. 文档已漂移：每日工单仍写 `rescore_refresh.py` 每小时，实际 crontab 是每 3 小时。
7. 平台状态账本分散：视频号主表、抖音账本、快手账本、手工 catchup 日志、平台后台证据没有统一“窗口级结果”视图。
8. 抖音 UNCERTAIN/UNDER_REVIEW 队列过大，会在每日主任务里制造噪音，容易掩盖“今天到底有没有按窗口发新片”。

## 4. 建议审核项

### A. 先确定窗口规则

需要你拍板早窗到底采用哪一个：

- 方案 A：保留当前 `.env` 的 `06:30-09:00`，优点是容错大，缺点是与 7 月 28 日调研文档不一致。
- 方案 B：回到调研文档的 `07:00-08:00`，优点是规则更窄更干净，缺点是必须重配早窗执行器，且候选稍晚出现更容易错过。

无论选哪一个，都应同步 `settings.py` 默认、`.env`、crontab 注释、`docs/publishing_timing_research_2026-07-28.md`、`docs/daily_ops_workorder.md`。

### B. 把“窗口执行者”改成巡航式

推荐把主发布入口改成窗口内每 10-15 分钟触发一次，例如：

- 工作日：06:35-08:50、11:20-12:35、17:05-18:05、19:05-20:35。
- 休息日：09:35-10:50、13:35-16:20、19:05-21:20。

流水线已经有窗口守卫和任务锁，重复唤醒可以保持幂等；真正需要补的是“窗口内无候选时稍后再看一次”。

### C. 增加发布窗口审计器

新增一个只读检查命令，日报和 CI 都可以跑：

- 读取当前 `.env` 有效窗口。
- 读取 crontab 或版本化调度清单。
- 判断未来 7 天每个发布窗口是否至少有一个执行点。
- 标出执行点在窗口外、只有一个执行点、休息日/补班日错配、已禁用平台仍有专用执行器等问题。
- 异常时 Telegram 告警：窗口名称、缺失日期、缺失执行者、建议修复。

### D. 建窗口级心跳表

建议新增本地只读/写入心跳，不替代平台证据：

| 字段 | 含义 |
| --- | --- |
| `window_date` | 北京日期 |
| `window_name` | morning/midday/evening/prime |
| `window_range` | 当日有效窗口 |
| `triggered_at` | 执行者启动时间 |
| `candidate_count` | 启动时高分候选数 |
| `wechat_published_count` | 本轮本地确认视频号成功数 |
| `douyin_submitted_count` | 本轮抖音提交数 |
| `blocked_reason` | 无候选、非窗口、登录失效、审查失败、平台不确定等 |

日报应从这个心跳表回答“这个窗口有没有执行者、有没有候选、有没有发布、为什么没发”。

### E. 把调度事实版本化

把 Video Pipeline 相关 crontab 迁到版本化配置，至少保留：

- `scripts/install_*_schedule.sh` 生成的最终调度。
- `docs/daily_ops_workorder.md` 自动引用同一份调度清单。
- 审计器比较“安装中的 crontab”和“仓库期望调度”。

## 5. 审核结论草案

我建议把问题定义为：发布规则不是单一 bug，而是“时间窗口规则、执行者和结果证明三者没有统一账本”的机制问题。

优先级建议：

1. P0：确定早窗口径，并同步代码默认、`.env`、文档、crontab 注释。
2. P0：增加窗口执行者审计，先做到“有窗口无人执行”当天报警。
3. P1：把单点触发改为窗口内巡航式触发。
4. P1：新增窗口级心跳表，让日报解释每个窗口的结果。
5. P2：治理抖音 `UNCERTAIN`/`UNDER_REVIEW` 队列，降低主任务噪音。
