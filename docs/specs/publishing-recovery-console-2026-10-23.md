# 后台发布恢复：本次复盘与已确认规格

日期：2026-10-23（北京时间）

整理：Codex（具体模型版本未知）

状态：**用户已于 2026-10-23 确认按本规格开发、验证并上线。** 实施与运行采用证据见 `docs/acceptance/publishing-recovery-console-2026-10-23.md`。

## 目标与交付责任

用户希望在后台完成额度重置、今天／最近 24 小时失败重试、冷却与避让恢复，不再需要 AI 逐次编辑状态文件、调用隐藏 API 或解释反复回队。

本次把 `i1WsMclsgOs` 的技术问题修复并推动到实际发表动作，但恢复最后一步依赖 AI 手工操作账户状态。这是交付缺口：修复个案没有形成用户能独立使用的恢复流程。以后验收必须包含“用户只通过后台完成同类恢复”，不能仅以测试通过、上线或一次人工操作结束。

本次发表事实见 [单片验收记录](../acceptance/retry-framed-caption-2026-10-23.md)：19:02:20 点击发表后为 `UNCERTAIN`。该片必须作为批量恢复排除反例，不得为演示新功能而重新上传。

## 已核实的根因

| 缺口 | 当前证据 | 用户受到的影响 |
| --- | --- | --- |
| 准入判断不一致 | `WeChatRequestGuard.cooldown()` 只计算 `blocked_until / next_session_at`；真正的 `wechat_account_schedule.admission()` 还检查滚动额度、恢复期、排队与提交记录 | 页面可显示允许执行，上传入口却拒绝，形成反复回队 |
| 原因被合并 | `pipeline_manager` 将退出 11 统一写成“同账号浏览器会话占用”，但额度拒绝也可能走此返回码 | 用户无法判断该等、该重置什么，还是确有任务占用 |
| 既有操作不完整 | `/wechat-cooldown-settings` 已能改策略、显示会话用量、确认解冻；`acknowledge_unfrozen()` 不重置滚动会话数，页面也缺少额度重置动作 | 修改上限、解除恢复期与清零使用量容易混淆 |
| 状态展示遗漏额度阻塞 | 冷却设置的 `effective_until` 与前端状态分支没有纳入额度恢复时间；可能同时显示额度耗尽和“空闲 · 可立即发布” | 数字与结论互相矛盾 |
| 批量重试未形成后台闭环 | `retry-recent` 和只读 preview API 已存在，前端没有对应完整流程；preview 仅给前 10 条，执行重新查询而不绑定预览目标 | 无法准确预览全部影响、选择范围并追踪执行结果 |
| 时间口径不足 | `get_failed_videos_since()` 按 `updated_at` 筛选当前 FAILED / LOGIN_REQUIRED，没有专门失败时间 | 后续更新会改变“今天失败”的归属，今天和最近 24 小时也无法清晰区分 |
| 重置不等于真正恢复 | 旧批量接口只改为 PENDING，仍依赖分数、任务资格、发布时间和后续调度 | 提示重试成功后，任务仍可能没有执行，原因不明确 |

此前已修复的人工审批归因、ASR／翻译检查点复用继续保留。本轮重点是让发布恢复可观察、可操作，并消除准入与调度之间的断层。

## 推荐入口与操作方式

扩展既有 **配置与运维 → 冷却与调度**，将其命名为 **发布恢复与调度**，保留原 URL 兼容。生产队列的“出错异常”和“待发布”提供带当前筛选条件的入口。沿用 `DESIGN.md`、`UX-CONTRACT.md` 的主题、字号、导航及原生对话框，不另做一套后台。

页面由三部分组成：当前阻塞及可恢复时间、恢复操作、任务与操作记录。用户先看到“现在为什么不能执行”和对应动作，详细策略参数放入已有设置区域。页面读取和预览不访问视频号、不启动任务、不消耗平台额度。

### 1. 显示全部阻塞与准确时间

- 统一显示本地滚动 24h 有效用量／上限、过去 24h 实际会话数、最近重置、稳定期／恢复期、会话间隔、平台限流退避、排队位置、真实会话占用、发布暂停／维护和加工避让。
- 同时存在多个阻塞时逐项展示；恢复时间取全部适用且可计算限制的最大值。真实占用或外部平台恢复时间未知时明确写未知，不给出虚假的“现在可发布”。
- 发布页、手动执行、自动 ready-worker 与上传器共用同一份准入计算与原因码。后台预览是纯本地计算，不因读取而入队或登记平台会话。
- 等待属于“加工完成 · 等待额度／间隔／排队”等具体状态。只有真实执行阶段才显示制作中；保留有效审批和所有仍有效的阶段产物。

### 2. 额度、冷却和退避的独立重置

| 按钮 | 实际效果 | 确认时必须说明 |
| --- | --- | --- |
| 重置本地 24h 额度 | 从本次重置建立新的本地计费基线，有效用量归零；后续会话照常计数 | 这是账户共享的访问额度，包含发布、登录等会话；不是已发布视频数量，也不能重置平台自己的限制 |
| 清除本地冷却与退避 | 清除本地访问间隔等待、限流退避级数及恢复期；保留历史触发证据 | 平台实际状态未知，下一次原生 -360／429 仍立即停止并重新进入退避 |
| 重置全部本地发布限制 | 组合上述两项，一次确认、一次审计；保留策略上限和常规调度频率 | 展示具体账户、前后变化及仍会阻塞的条件；既有已授权自动队列可能因此恢复 |
| 重置后重试所选任务 | 先确认完整目标列表，再执行组合恢复并交给正式队列 | 只对选中任务新增本次恢复授权；不把所有历史失败或其它账户一起恢复 |

“恢复推荐默认”继续用于策略配置，不能冒充额度重置。“确认平台已解冻”不能冒充一次平台核验；本地恢复的提示不得声称平台已解冻或投稿已成功。

重置采用可审计的新基线，不删除原始会话和审计历史。展示“实际访问”与“重置后有效用量”，避免清零后把历史访问也显示为不存在。既有共享会话设计暂不拆分为新的发布／登录／互动独立预算；评论与回复专用六小时间隔保持原样。

重置自身不创建新发布授权。若既有自动队列会恢复，在确认中明确提示；组合操作先登记所选任务的恢复优先次序，避免释放额度后立刻被其它任务抢占。

### 3. 今天／最近 24 小时失败批量重试

1. 选择 **今天（北京时间 00:00 至预览时刻）／最近 24 小时／自定义时间**。预览固定起止时间，并显示时区；两种快捷窗口不是同一个条件。
2. 展示所有匹配任务，支持分页、全范围选择与取消选择；明确区分“本页”和“全部匹配”。每项有视频及切片身份、失败时间与来源、当前失败阶段、可复用产物、批准状态、阻塞原因和建议动作。
3. 服务端分类：**可直接续跑／恢复后可续跑／需登录或人工处理／已有提交证据禁止重投**。默认只勾选已具备任务及发布资格的前两类；恢复后可续跑的条目必须说明本次操作会解除哪些限制、哪些仍需等待。
4. 一次确认本次所选范围、将恢复的本地限制及执行后果，创建持久批次。正常操作不再逐条要求 AI 授权，也不连续弹多个等价确认框。
5. 后台按正式调度逐项领取。成片就绪的任务直接进入发布检查；缺失或失效产物从最早失效步骤继续。用户明确选择重试的任务获得绑定本批次的一次恢复意图，不再因仅改 PENDING 且低于自动评分线而悄悄搁置；不修改原分数或准入来源。
6. 批次页显示已排队、实际开始、等待及最早时间、已执行发表动作待确认、明确失败、跳过及原因。接受批次、进入队列、点击发表、平台受理与公开可见分别表达。
7. 用户可取消尚未启动的条目；不撤销已发生的外部提交、不终止正在提交的浏览器。刷新页面或服务重启后可继续查看同一批次，重复点击不生成重复批次或上传。

批量执行保留日常限额与频率。额度只重置一次，不能每轮自动清零；超过本轮额度的任务继续排队。新的原生平台限流暂停该账户后续尝试，保留进度并显示恢复入口，不形成自动重置循环。

“失败时间”新增明确记录，与普通更新时间分开；保存每次失败及恢复尝试，不在改为 PENDING 时抹掉历史。旧数据缺少失败时间时，明确标为“按最后更新时间估算”，列为可手动纳入的历史候选，不能冒充精确失败时间。

安全边界逐条展示并由后端再次检查：

- `UNCERTAIN`、`UNDER_REVIEW`、已受理／已发布、存在提交意图或原生回执的任务始终不进入自动重投；本次 `i1WsMclsgOs` 必须被正确排除。
- 内容审批缺失或失配、素材或封面质量失败、商品绑定失败等不能靠重试授权自动放行；给出已有专用处理入口。
- 已在途、有活动租约或真实锁占用的任务不重置；状态在预览后变化时单项跳过并解释。
- DISCOVERY、黑名单、已删除任务不会因批量重试被提权或复活；已生效人工批准不因技术恢复丢失。

### 4. 冷却以外的“避让”

| 等待类型 | 后台可操作行为 | 边界 |
| --- | --- | --- |
| 调度队列优先级 | 让所选任务优先尝试一次，保留其它任务及其顺序记录 | 不能抢占正在提交的浏览器，也不能让同一账户并发发布 |
| 提交前失败的任务退避 | 有持久凭据证明尚未提交时，解除该任务下一次等待并重试一次 | 不清除已经产生的提交意图；新增失败继续按有界重试处理 |
| 制作阶段的美股盘中／重负载避让 | 显示北京时间和原时区；默认继续等待，可显式选择仅对本次选中任务跳过一次软避让 | 不永久关闭整机保护；一次只启动一项重负载任务；不修改 OptionSense 或其它项目策略 |
| 已加工完成的成片 | 直接走既有独立发布执行者，明确标注不需要等待制作避让 | 仍遵守账号额度、冷却、登录、平台暂停和发布门禁 |
| 真实浏览器锁、活动进程租约、维护态 | 显示实际持有者和任务入口；等待释放或进入既有维护处理 | 不提供强删锁、一键杀进程或绕过未知运行状态的按钮 |

一次软避让许可绑定账户、任务／切片、批次、适用限制及当前版本；仅供下一次启动，最长 30 分钟未消费即失效。到期条目回到正常排队并明确显示原因，不自动续签或影响其它任务。

## 范围与本轮不做的改变

- 本轮完整交付当前 **YouTube → 视频号主流水线，含切片** 的后台恢复闭环，支持桌面与手机操作。
- 其它独立制作／A/B 实验／抖音发布记录标明所属流程并跳转既有专用入口，不混入本批次；新增这些流程的统一恢复适配另行确认，不承诺本轮重发所有类型。
- 不关闭内容审查，不改已批准的字幕版式，不重做有效产物，不改变阈值或频道准入，也不恢复发布后自动平台查询。
- 所有“平台结果待确认”继续走已有人工核实流程；重置按钮不改变其投稿身份和结果。
- 本轮不实施一个无差别“清掉所有保护”的开关，也不永久提高账户配额。组合按钮可覆盖上述本地运行限制，但保留互斥、审批与防重复提交。

## 实现约束与复用边界

推荐依赖方向：`web / scripts → 发布恢复服务 → PipelineDB + 账户准入策略 / RequestGuard → settings`。不从领域层导入 web、scripts 或 cli，不继续往大型 app.py 堆独立业务分支。

- 现有冷却设置页面、单片确认与失败重试 API 复用同一恢复服务；保留兼容参数，旧入口不能绕过新准入与防重检查。
- 一套纯准入评估供页面、预览、自动调度和上传器使用，返回全部阻塞、可用动作、恢复时间或未知原因；只读评估不修改真实队列。
- SQL 及状态事务只在 DAL。新增失败时间／事件、批次和逐项状态采用可恢复的增量结构，不用业务代码直接改库或一次性重建数据库。
- 账户重置在原生账户状态锁内原子执行，绑定预览版本并保留前后摘要；预览后出现新限流或新会话时拒绝陈旧重置，先刷新再确认。
- 跨状态文件与数据库的组合恢复用持久操作 ID 和分阶段回执恢复，明确部分完成，不宣称跨文件原子事务。请求超时后先查询原操作结果，不能盲目重复重置。
- 批次固定明确选中的身份及版本，执行时再次核实；新失败不自动扩大已确认范围，提交记录出现后立即阻止再次领取。
- 原本地临时操作脚本不作为正式后端入口；额度重置采用受测公开方法，记录来源、时间、范围、重置前后摘要、批次和逐项结果，不记录凭证。
- 复用已有主题、原生 dialog、焦点恢复、URL 筛选及局部反馈模式。状态过期或读取失败时保留可读记录并标注，禁止依赖旧结果执行；桌面和手机均能查看完整原因及处理部分失败。

## 用户任务验收

| 场景 | 必须观察到的结果 |
| --- | --- |
| 冷却已到期、滚动额度 50/20 | 页面显示额度耗尽及正确恢复时间；手动和自动入口均不反复启动上传器，不误报浏览器占用 |
| 后台重置本地额度 | 有效用量归零、历史访问仍可查、上限不变；下一次会话变为 1/20；提交记录和其它排队任务保留 |
| 清冷却但尚有其它阻塞 | 页面明确显示剩余阻塞，不能提示全部恢复或已发布 |
| 选择今天和最近 24h | 跨午夜边界结果正确；失败时间与更新时间分离；历史估算任务有明确来源标识 |
| 预览 30 项、仅选 6 项 | 只创建这 6 项的恢复意图，包含切片精确身份；分页和刷新不丢选择口径；新增第 31 项不被顺带恢复 |
| 混合技术失败、待审、在途和提交未知 | 技术失败按资格续跑；其它项分别解释并跳过；`i1WsMclsgOs` 的既有提交意图和 UNCERTAIN 不被清理 |
| 已有成片再重试 | 文案、Whisper、翻译与完整渲染调用次数为 0；界面显示复用并进入发布检查 |
| 缓存损坏或源变化 | 从最早失效步骤继续，并显示原因；审批仍按原绑定规则核验 |
| 有资格的低分历史失败被明确选中 | 按绑定一次的人工恢复意图执行，不改分数、不让浏览类来源进入生产 |
| 批量恢复超过剩余额度 | 正常排队并显示预计时间，不在每轮自动清零、不同时打开多个浏览器 |
| 新的 -360／429 | 本次立即停止，后续待办暂停，页面显示最新限流；陈旧确认不能清掉新事件 |
| 两标签页同时操作、网络超时、进程重启 | 同一操作 ID 可查，重复点击不双重执行；清晰报告部分完成、版本变化或待确认 |
| 盘中成片与未加工任务混合 | 成片走独立发布；重负载任务等待或仅按明确许可启动一次；活动锁和其它项目保护保留 |
| 用户仅用后台操作 | 从查看阻塞、选择今天／24h失败、重置、重试到查看逐项结果全程不需要 AI、终端或直接编辑状态文件 |

实现后使用项目隔离测试入口覆盖上述边界与真实 Chromium 交互，检查 390px 手机、桌面、键盘取消／确认、主题和部分失败状态。上线必须有实际运行采用回执；测试中的平台路由使用隔离夹具，不借验收提交真实历史视频。

本方案的实现与验收以本地后台操作闭环为准。真实平台投稿仅在已有适用授权或用户在后台明确确认的具体批次范围内执行，点击、受理与公开结果仍逐级区分。
