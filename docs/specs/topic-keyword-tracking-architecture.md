## 1. 目标、事实和取舍

运营者在管理后台保存自己关心的专题关键词，按需搜索近期 YouTube 视频，在一个候选池里查看、收藏或排除结果，减少逐条寻找视频的工作。首期要证明“找得到、看得清、留得住、停得下”，并证明任何候选动作都不会启动制作或发布。

2026-10-11 已核实：生产后台运行于 `:9100`；现有热词面板只读，现有频道目录读取使用 Data API 与 RSS。20 个现存工作区中尚未找到 `topic_tracker`、专题候选 DAL、管理页面或专项测试。现有 Dashboard 的同源检查不是完整操作者鉴权；本功能不能仅沿用它就宣称审核入口安全。`settings.is_us_market_guard_window()` 已存在，不能另外硬编码美东时间窗。项目实际 Cloud 配额、可用额度和其他调用者消耗尚未核实；本轮不读取密钥或发起生产搜索。

已确定的约束：按评审完善规格、用户确认后开发；遵守受众定位、DAL 封装、单向依赖、隔离测试和现有主流水线保护。以下数量、界面布局和简化项属于用户已确认方案。

| 推荐取舍 | 原因及代价 |
| --- | --- |
| 产品名称使用“关键词追踪 / 专题候选”，不称内容放行白名单 | 命中关键词仅代表发现线索，不能授予加工或发布权限 |
| 首期只手动搜索，暂缓定时巡检、紧急档位和自动补跑 | 先验证候选的实际价值与预算；运营者需主动点击搜索 |
| 首期不调用 Gemini 或其他模型，不产生 AI 分数、中文翻译标题或受众自动判定 | 降低成本与不确定性；运营者自己判断相关性、可信度和受众适配 |
| 收藏表示选题意向；没有“纳入管线”、加工批准或发布批准 | 满足评审对候选工作台的边界；制作移交留到后续单独规格 |
| 新增独立页面，保留现有热词展示和频道管理 | 避免把只读热词、频道信用和专题检索混成一套权限 |
| 新页面首期仅允许本机访问与写入 | 不把局域网同源检查视为身份认证；手机/远程管理后续另定 |

## 2. 首期范围与用户流程

**包含**：专题新建与编辑、暂停/恢复、归档、有效期；有预算的手动搜索；视频详情补齐；跨专题防重；候选浏览、筛选、收藏/取消收藏、排除；搜索记录、预算、失败原因和操作审计。

**暂缓**：定时搜索、自动热点发现、HN 热词自动导入、同义词或多语言自动扩展、AI 打分、素材下载、转写、字幕、成片、封面、Telegram 通知、Bot/CLI 写入口、进入 `processed_videos`、任何上传或发布。既有业务入口的权限与行为不因本功能而扩大。

主流程：

1. 打开“关键词追踪”，看到已有专题、候选数量、最近搜索、当前可用预算与运行状态；首次进入是空状态，无自动导入或自动请求。
2. 新建专题，例如名称“鼠疫追踪”，查询词 `plague outbreak`，选择类别、搜索时间范围及有效天数。保存只保存配置。
3. 点击“搜索候选”。页面立即显示本轮状态；相同搜索重复点击返回同一运行记录，不重复扣预算。被暂停、过期、预算不足或保护窗口阻挡时给出原因。
4. 在候选卡片查看原始标题、频道、发布时间、真实时长、播放/点赞统计、命中专题、规则提示及数据更新时间，打开原视频核实内容。
5. 对可核实候选点击“收藏”或“排除”。收藏旁明确标注“仅保存选题意向”。没有任何制作或发布按钮。
6. 暂停专题或关闭搜索后，后端停止领取新请求；已有请求在有界时间内结束，界面区分“正在停止”和“已停止”。

## 3. 专题、候选与整理规则

### 3.1 专题字段与默认值

| 字段 | 约束与推荐默认值 |
| --- | --- |
| 名称 | 必填，1–40 字符；允许名称不同但查询词相同的提示，不允许重复创建相同查询条件的有效专题 |
| 查询词 | 必填，1–120 字符；保留用户填写的原文，去首尾空白、合并多余空白；防重使用 Unicode 归一化与大小写归一化，存储保留原文 |
| 查询表达式 | 一个专题一个请求表达式；用户可明确填写 YouTube 支持的 OR/排除词；无模型改写、自动拆词或后台多次扩搜 |
| 类别 | 宏观经济、科技产业、商业历史、健康科学、地缘战略；不代表已通过受众判断 |
| 发布时间范围 | 最近 3/7/30 天，默认 7 天；按每轮开始时刻固定边界 |
| 有效期 | 默认 7 天，可选 1–30 天；到期停止搜索，保留候选与审计；后台存 UTC，界面显示 Asia/Shanghai |
| 状态 | ACTIVE（可手动搜索）、PAUSED、EXPIRED、ARCHIVED；恢复过期专题必须明确设置新有效期 |
| 容量 | 最多 10 个 ACTIVE 专题；归档代替物理删专题，历史命中关系与决定不级联删除 |

编辑查询词、类别、时间范围或有效期会增加专题版本，既有候选不自动删除或重新整理。一次搜索绑定开始时的专题版本。暂停/归档即时阻挡后续请求；请求中允许暂停/归档，其他编辑提示稍后再试。

### 3.2 候选身份与数据限制

同一个规范化 YouTube 视频 ID 只有一个候选实体；同一视频可关联多个专题和搜索轮次。新增命中关系不产生第二张重复卡，不重置收藏或排除。同源视频是否已在主流水线，以 DAL 对源 ID 的实际只读查询为准，兼容 `(youtube_id, slice_index)` 的现有切片结构，不向主表新增全局唯一约束。

展示字段最少包括源视频 ID/链接、原始标题、频道 ID/名称、发布时间、真实时长、最近一次元数据获取时间、命中专题、整理状态和规则状态。播放量/点赞量缺失显示“未知”，不填 0；没有配音或字幕证据时语言显示“未核实”，英语搜索偏好不冒充英语内容验证。结果排序默认最近发布时间，允许查看官方统计原值，不生成播放量综合分、点赞率或推导热度。

标题、描述和规则提示均按不可信文本转义；外链只由规范化 ID 构造 YouTube HTTPS 地址。原视频仅通过显式点击打开，不嵌入自动播放，不下载媒体或缩略图到本地。

### 3.3 两个互相独立的状态维度

整理状态是 `NEW`（未整理）、`SAVED`（收藏）、`REJECTED`（排除）。规则状态是 `CHECKABLE`（可人工核实）、`INCOMPLETE`（资料/检查不足）、`RESTRICTED`（规则受限）、`UNAVAILABLE`（源视频不可用），另附只读 `pipeline_present` 标记。可人工核实只表示所需元数据与规则检查具备，不表示完整内容安全或可发布。

确定性检查顺序：规范化身份与跨专题去重 → 必要元数据 → 直播/预告/不可用检查 → 真实时长 → 已有内容审查与频道规则的元数据检查 → 主库/黑名单只读状态 → 人工查看。

- 保留原案的候选时长范围，按详情中的实际秒数检查 `180 ≤ duration ≤ 1800`；首期不可在专题表单放宽。超出范围标“时长受限”，不抹去搜索记录。
- 直播中、未开播或详情查询明确未返回的视频，不作为可收藏候选；详情请求失败或时长未知标资料不足，不能伪装成源视频已删除。
- 元数据命中现有 P0、其他现有阻断规则、频道排除策略或黑名单时标受限并展示依据；首期没有绕过按钮。审查方法复用当前规则，无修改现有词库或豁免项的授权。
- 规则模块、DAL 查询失败或必要字段缺失时标资料不足，禁止收藏；查看原链接和排除仍可用。不得把异常默认为通过。
- 主流水线已有记录的候选显示已有状态，只允许查看/排除，不允许收藏；不改其来源、分数、下载进度、切片或发布状态。
- 收藏绑定候选内容版本与当时规则版本。标题、描述、时长、可用性或规则结果变化时显示“资料已变化，需重新核实”；旧收藏不升级成新版本的确认。统计数字变化只更新统计时点，不使内容版本失效。
- 排除使用简短预设原因（不相关、来源不可信、不适合受众、已重复、其他）。首期不提供恢复排除；重复检索、专题归档后再新建、页面重载都不能自动恢复。
- 发现黑名单或主流水线已拒绝/封禁/已发布记录时，保留其事实标记；任何收藏、刷新或重新命中都不能复活主流水线记录。

## 4. 搜索源、预算与失败反馈

首期仅使用官方 YouTube Data API 的 `search.list` 与批量 `videos.list`。每轮一页，最多 25 条搜索结果；`type=video`、`order=date`、`safeSearch=strict`、英语相关性偏好，发布时间由专题范围决定；不使用 API 的 `medium` 代替实际 3–30 分钟检查。没有自动翻页、抓取兜底、AI 调用或 OAuth 写操作。

官方目前将搜索与上传分别放入独立桶，搜索默认每天 100 次，其他端点共享默认每天 10,000 units；日界为太平洋时间午夜。项目实际额度须以其 Cloud 控制台为准，不能直接把默认值当作本项目余额。[官方配额说明](https://developers.google.com/youtube/v3/determine_quota_cost)

| 首期内部限制 | 推荐值与行为 |
| --- | --- |
| 搜索日预算 | 全模块 20 次/太平洋日期；实际确认可分配额度更小时取更小值 |
| 其他端点日预算 | 全模块 40 units/太平洋日期，仅限必要批量详情/明确的失败重试；不得使用上传桶 |
| 单轮请求 | 最多 1 次搜索＋1 次批量详情；搜索失败不自动重搜；详情临时失败最多重试 1 次且仍计预算 |
| 并发 | 全局最多 1 个搜索作业；同轮重复操作复用作业，其他专题提示忙，不建立无界队列 |
| 冷却 | 同专题完成或失败后 15 分钟内不另起搜索；保留上轮结果、准确提示可再次搜索时间 |
| 超时 | 每个外部请求最多 20 秒，每轮最多 60 秒；总截止时刻与保护窗口剩余时间更短时采用更短限制 |
| 预算预留 | 发请求前短事务原子预留；可能已发出而响应丢失仍按已消费记账；未发出且有确定证据时才撤销预留 |

20 次/天是内部运营上限，不是“2,000/3,500 API units”的换算。预算按逻辑 Cloud 项目、资源桶、`America/Los_Angeles` 日期持久化，包含所有本模块入口、重试和元数据刷新；不能靠进程内计数或 UTC 日期重置。预算预留与结果入库分别使用短事务，网络调用不持有数据库写锁。重启不清零，夏令时由时区库计算。

旧调用者未统一接入预算治理前，只能证明“本专题模块不超额”，不能承诺全项目硬预留。生产开放前需登记共享同一 Cloud 项目的调用者和可分配额度；无法确认余量则保留离线/关闭状态。配额耗尽、API 未配置、凭据无效、网络失败、保护窗口、规则失败、数据库忙分别显示可理解的原因；成功零结果与搜索失败必须不同。错误和审计不保存带密钥的 URL、请求头或完整原始异常。

## 5. 运行、暂停与本机操作边界

全局只有 `OFF` 和 `DISCOVERY_ONLY` 两种模式，默认 `OFF`。OFF 可查看保存的资料、维护专题和整理候选，不允许任何外部搜索/补详情请求；本地到期清理仍执行。DISCOVERY_ONLY 只接受明确的本机手动搜索。本期不定义准入模式。页面打开、GET、收藏、创建或恢复专题均不触发外部请求。

创建作业、每次外部请求前和提交候选前检查模式、专题版本/状态、预算与 `settings.is_us_market_guard_window()`。真实搜索要求现有宿主保护机制可用且开启；它未开启、不可判定或检查报错时阻挡搜索，不能当作窗口安全。

暂停/关闭后不再发出下一请求；已发请求最长在 20 秒超时内结束，随后最多 5 秒完成本模块停止状态记录。页面在此期间显示“正在停止”，不提前报“已停止”。进入保护窗口时采用同样边界；已完成的本地数据处理只能是有界短事务。已完成的完整轮次结果可以保留；中断轮次记录 PARTIAL/INTERRUPTED，不把失败详情拼成完整候选。恢复后没有欠账补跑、后台排队重搜或通知。

进程退出或重启后过期运行记录转为 INTERRUPTED，保留已预留预算，释放本模块作业占用；不自动续跑搜索。作业并发控制同时防住多浏览器和多进程，不能用过期 lease 覆盖仍活着的作业。不得给现有流水线、上传器、浏览器或 OptionSense 进程发信号。

本机操作边界：新页面/API 校验真实对端为回环地址，不信任客户端的转发头；写操作还需要服务端签发的本机会话、限定 Host/Origin、CSRF 校验与候选/专题版本校验。会话只在本机建立；无会话、无 Origin、过期会话、错误 CSRF 和局域网来源写请求均拒绝，错误不会修改数据。既有后台其他页面不在本期重做鉴权。

不复用 Telegram、流水线 lease 或发布器令牌，不向浏览器暴露长期密钥。操作审计记服务端会话标识而非伪造用户名；会话标识不代表实名审核人。首期没有远程/手机/多角色审批；该限制在本机以外的页面中给出明确提示。

| 搜索作业 | 请求幂等键、专题版本、起止时间、状态、结果计数和不含密钥的失败码 |
| 预算账本 | 项目/桶/太平洋日期、预留/消费状态与作业关联；多进程原子校验 |

纯领域包导入不得建表、启动线程、读密钥、访问真实 output 或发请求；DDL 和作业启动是明确的初始化/运行阶段行为。配置只在 `settings.py` 声明并补 `.env.example`；Web 使用独立 router，`app.py` 只挂载，不往核心 FSM 塞条件分支。不引入通用工作流引擎、消息总线、第二个数据库或新服务端口。

API 元数据与本地整理记录分离。按官方数据刷新/删除要求，API 获取的字段在 30 个日历日内刷新或删除；首期不为过期数据自动发网络请求。每天执行有界本地清理，删除过期标题、描述、统计、链接/ID等可还原源数据及原始快照；保留本地决定的不可逆匹配键、版本摘要和操作时间以防排除复活。再发现同源时重新获取当前元数据，保留本地排除决定。不把审计副本当成无限期保存旧 API 数据的途径。整个服务停机后首次启动应先清理再提供页面；页面提示数据截至何时，缺失即未知。[数据存储要求](https://developers.google.com/youtube/terms/developer-policies)

### 11.2 一个持久化维护闸门，明确暂停和恢复

推荐采用**本机持久化控制状态 + 短时跨进程互斥**，与候选数据库分开，使候选数据库故障不能自行打开维护闸门。控制文件建议为 output/maintenance-state.json，路径由 settings 的 typed 字段及样例配置统一声明；状态只含版本、维护原因、操作时间和非秘密归属，不保存环境、密钥或浏览器凭据。文件替换与状态转换须原子化；具体实现保持在一个低层门面，不由 Web、Bot、脚本各自复制逻辑。

| 状态/显示 | 语义 | 允许的操作 |
| --- | --- | --- |
| RUNNING | 显式恢复后的正常状态；仍遵守全部现有业务保护 | 按原资格和调度领取；候选搜索仍由自身 OFF/flags 拒绝 |
| MAINTENANCE / 排空中 | 闸门已关闭，有既有在途或等待资源的已接纳工作 | 既有单项自然结束、必要回写；本地状态查看及健康的候选本地操作 |
| MAINTENANCE / 可验收 | 无在途、有效持锁、待启动接纳项；所有来源已覆盖 | 本地候选管理、浏览器验收、正常退出与维护启动 |
| UNKNOWN / 不能证明空闲 | 控制状态缺失/损坏/不可读，状态采集失败，归属或进程存活不能确定 | 只读诊断；拒绝新领取和恢复，不显示“已排空” |

新代码首次使用时必须显式初始化控制状态，推荐先初始化 MAINTENANCE；缺失不是 RUNNING。普通启动、热重载、崩溃拉起以及启动参数不带维护标志，均不能把已经保存的 MAINTENANCE 清掉。只有显式本机恢复命令才能转换到 RUNNING；无定时到期解锁、自动恢复或绕过参数。重复进入维护幂等；恢复携带预期版本，旧版本冲突拒绝。状态不可可靠写入时，命令失败，不报成功；状态不可读取时，执行入口拒绝新领取。

已实现的操作契约（来源回执格式见[覆盖清单](../handoffs/2026-10-12-topic-candidates-rollout/MAINTENANCE-COVERAGE.md)；本轮不在生产执行）：

- ./vpanel maintenance enter --reason "候选工作台关闭状态验收"：先持久化暂停新领取，返回版本与排空状态；不等于停服务或已空闲。
- ./vpanel maintenance status --evidence /absolute/path/sources.json：列出控制状态/版本、覆盖的执行者、在途/等待项、真实持锁与未确定项；无秘密输出。无可信来源回执或空闲判定失败时退出非零。
- ./vpanel ui start --maintenance：启动前持久化维护状态；继续使用原端口与 launchd 路径，不创建第二个后台。已存在正常运行的旧 UI 时不得借此强杀替换，应明确拒绝并报告。
- ./vpanel maintenance stop-ui --evidence /absolute/path/sources.json：仅在已证明可验收、相关重拉起来源受控时，对已确认的空闲 UI 按正常生命周期退出；最多等待 15 秒，仍未退出则失败并保留现场，没有 SIGKILL 分支。
- ./vpanel maintenance resume --expected-version N --evidence /absolute/path/sources.json：只有状态采集可信、在途/等待为空、旧保护有效且相关验收完成，才显式恢复 RUNNING；返回新版本。此命令不操作候选模式或搜索配置。

恢复操作仅在本机 CLI 提供，依赖宿主账号权限；页面只显示维护状态与拒绝原因，不新增能恢复业务的远程 HTTP/Bot 接口。进入维护不修改市场避让、发布暂停、商品/内容审查或任何原业务授权。

### 11.3 暂停边界、竞争窗口和必须覆盖的入口

“新领取”按单视频、单审核项、单研究/加工任务定义。已有批量进程完成当前单项后，领取下一项也须重新检查闸门；不能以整批早已启动为由继续处理所有剩余项。已发的网络请求、当前下载/渲染/上传与必要的同一任务回写自然完成；后续独立发布、通知补偿或恢复任务属于新领取，维护期间不再派发。

在途定义不截断原单项 FSM：已接纳的单视频按原授权完成既定阶段，可能包含尚未开始的后续阶段；全程计入排空，不提前宣称无上传。其子进程与必要回写须绑定原接纳项和对象，不能借该归属启动另一视频或独立审核项；过期、伪造或不匹配归属不能作为维护豁免。

进入维护与执行者最终准入必须使用同一个短互斥边界，并记录接纳项归属：在暂停提交之前已接纳的项计入排空；之后的项不创建任务或执行子进程。检查闸门后等待资源的项也不能被空闲统计漏掉；资源锁获取后、单项领取前再核对状态，取消尚未开始项不能改变业务资格。不能只在 Web startup 或进程启动时检查一次。互斥不得跨越网络调用、制作、上传或长时间排空。

| 来源 | 维护期间必须阻止 | 保留与核对 |
| --- | --- | --- |
| Web 全管线/队列循环 | 启动首次自动执行、后续轮询领取；队列中的孤儿改写、通知补偿、purge 等自动写动作 | 本地只读状态；当前任务必要回写 |

“来源→入口→接纳点→排空证据→恢复方式”已记录在[覆盖清单](../handoffs/2026-10-12-topic-candidates-rollout/MAINTENANCE-COVERAGE.md)，包含 Web 自带任务、脚本直接入口及独立子进程；未知或未接入来源使“可验收”判定失败。维护闸门不承担阻止任意手工直接运行 FFmpeg 或修改文件的操作系统沙箱职责；此类进程若存在，须列为未受控来源并延期变更。

**首次采用的边界**：当前已加载的旧进程不认识新闸门。独立测试证明新代码正确，不能证明旧生产已暂停。未来 A 执行前仍须停止外部新触发与人工业务入口、识别全部旧执行者及再拉起来源、让在途自然结束，并用真实进程/锁/账本确认退出窗口受控；不能往旧工作区放一个状态文件就宣布生效。若无法证明旧 Web/独立发布的竞争窗口受控，延期 A，另交首次采用操作方案，不通过强杀、删锁或批量改任务状态解决。

### 11.4 候选模块运行故障隔离

已知候选运行故障包括：锁文件权限不足、路径被目录占用、open/flock 的可预期 I/O 错误；候选连接、PRAGMA、初始化 DDL/维护事务的数据库忙、只读与操作失败。覆盖从连接创建到资源释放的完整路径，在候选 DAL/门面边界转换为脱敏错误；不一概捕获所有编程错误并当作成功。

- 旧后台可用、故障局限于候选时，应用继续启动，旧本地 GET/控制面保持既有行为；候选页面/API 返回明确 503 与稳定错误码，不能返回 200 空列表冒充“无候选”。候选所有业务写入、搜索与预算预留拒绝；安全检查仍先执行，非回环/非法会话不能获得故障详情或绕过拒绝。
- 整个共享数据库或磁盘不可用时，旧业务也可能受损；明确标为共享故障，不承诺旧业务仍正常，也不能仅凭候选 503 宣称故障隔离成功。维护状态独立保存，采集不可信时保持 UNKNOWN。
- 状态记录初始化/清理最近成功时间、最近失败时间与脱敏类别。锁错误用 LOCK_UNAVAILABLE，数据库忙沿用 DATABASE_BUSY，其他候选数据库操作用 DATABASE_ERROR；不输出完整原始异常、绝对业务路径、URL/请求头或凭据。
- 初始化单飞；失败后至多每 60 秒有界重试一次，页面刷新/并发请求不得制造额外初始化风暴。SQLite 单次锁等待不超过现有 2 秒；隔离故障场景中启动/候选失败响应在 10 秒内完成。该指标不承诺任意硬件卡死可由 Python 强制解除。
- 初始化与清理只用真实短事务；失败不得遗留“可用”半初始化状态。成功重试先完成候选表校验、到期清理、孤儿作业回收与有效 OFF 核对，再恢复页面。清理失败时不继续显示到期 API 字段；清理任务不会因一次已知错误永久死亡，下一周期可恢复。
- 退出时 OFF 落盘失败要如实记录“停止状态未回读”，仍释放已取得的锁/连接，并按 v0.2 的在途请求停止边界等待；不能因本模块退出异常向旧业务进程发信号。故障后的恢复不自动搜索、不清预算、不删除收藏/排除/审计。

### 11.5 验收后的恢复与回退顺序

未来 A 仅在单独获得生产采用确认后执行：先在独立目录按**最新生产 main + 相关未提交差异**整合并隔离重验；版本变化时重新核对重叠，不将 17e01c4 永久固定为部署版本。保护既有词汇字段、商品约束、任务停止/刷新行为与无关文件。

维护进入→来源受控→自然排空→一致性 SQLite 备份/恢复点→采用→维护启动→本机候选 CRUD 与一次维护重启→故障/关闭状态与真实 LAN 拒绝回读→记录恢复前证据→显式恢复闸门及原外部调度→恢复后回读。生产不制造故障、渲染或公开投稿任务来验收；故障注入和业务领取演练放在隔离根。

恢复前：确认后台版本/hash/启动时间/cwd、新入口、本机边界与迁移回读通过；无未知执行者、在途和有效持锁；实际保护可用；恢复清单有执行责任。全部保持 TOPIC_SEARCH_ENABLED=false、TOPIC_QUOTA_VERIFIED=false、TOPIC_QUOTA_PROJECT 空、OFF、search_open=false。数据库暂时不可读时仍拒绝候选，不能把 OFF 未回读称为通过。

恢复后：逐项对照原 cron/launchd/worker 状态，检查覆盖的内存线程与独立执行者只有一组，恢复来源不得重复实例化；下一次正常轮询按现有资格执行，不集中重播维护期间漏掉的时点。恢复 RUNNING 与旧业务执行不等于候选发现模式开启，仍需回读候选拒绝、无新增作业/预算与无候选来源主库写入。没有合适既有任务时只报告调度/闸门恢复证据，将实际领取观察列为待回读，不虚构完成。

任一验收失败：保持 MAINTENANCE 与搜索关闭，停止采用；回退专题模块差异并保留通过验证的维护闸门，不删除候选表/审计/排除，不整库覆盖维护期间的合法回写。若需回退维护闸门本身或启动不认识该机制的旧版本，必须另核实外部冻结与启动条件；无法证明安全就保持服务停用并报告，不能用“回滚”触发自动恢复。恢复旧调度必须具备正常运行条件并明确执行/回读，不静默遗留永久暂停。

## 1. 业务背景与问题定义

当前系统（Web 运行于 `http://localhost:9100/`）的核心视频供给机制是**白名单被动轮询**（监控 20 个高信用度 YouTube 机构频道，如 TED、WSJ、DW 等）。这构成了生产流水线稳定、高质、安全的基本盘。

然而，在面对突发公共议题或垂直爆发性题材时（例如近期大众高度关注的“**鼠疫** / Plague”、或前沿硬核科技“**Nvidia Blackwell 架构**”、“**美联储利率决议**”），系统暴露出严重滞后性：
1. **被动等待白名单更新**：若白名单频道未在第一时间发布相关视频，系统无法从全网主动感知并捕获该题材；
2. **人工录入成本高昂**：历史实证表明（数据库真实记录 ID: `5441`, `5488`, `5576`, `5577`, `5667` 均为“鼠疫”相关视频），此前所有热点视频全部依赖人工在 Web 端粘贴 URL 单条录入（`source='MANUAL'`）；
3. **内容安全隐患大**：历史样本 `5577`（*BREAKING: Russia denies reports of second plague case*）曾因触发敏感词拦截被安全引擎熔断。全网野生题材具有极高不可控性，若缺乏前置风控闸门，极易导致微信视频号违规封号。

因此，系统亟需建立一套**高内聚、低耦合、严防代码腐化、且具备配额硬隔离与多级风控**的「专题关键词追踪与候选准入机制」。

## 3. 五轮红蓝博弈深度对抗推演（Red-Blue Adversarial Matrix）

```
                                  ┌───────────────────────────┐
                                  │      红方：全方位渗透攻击  │
                                  └─────────────┬─────────────┘
                                                │
          ┌─────────────────────┬───────────────┴───────────────┬─────────────────────┐
          ▼                     ▼                               ▼                     ▼
   [1. 配额击穿与饿死]   [2. 特洛伊垃圾渗透]             [3. 并发主键脏写碰撞]   [4. 巨石状态机代码腐蚀]
          │                     │                               │                     │
          ▼                     ▼                               ▼                     ▼
   [配额硬切分预算池]    [两阶漏斗: 规则+AI]            [表级物理隔离+原子准入]   [独立模块+零侵入 Facade]

                                  │     蓝方：高内聚韧性防线   │

### ⚔️ 第 1 轮：配额击穿与主线业务饿死（Quota Starvation）
* **红方进攻**：用户配置 10 个热词，定时器每 30 分钟轮询。48 轮 × 10 词 × 101 units = **48,480 units/天**。凌晨即打爆 Google 10,000 配额上限，返回 HTTP 403 `quotaExceeded`。上午 9:00 白名单轮询抛错瘫痪。
* **蓝方反制**：
  1. **配额硬切分治理器（`QuotaGovernor`）**：将 10,000 units 划分为：白名单专用池（保留 5,000）、专题搜索池（上限 3,500，约 34 次搜索/天）、应急缓冲区（1,500）。本地文件 `output/quota_usage.json` 持久化计数，达阈值立即短路休眠。
  2. **时效分级调度**：按紧急度分为 `URGENT`（突发如鼠疫，4小时/次，TTL 3天）、`NORMAL`（12小时/次）、`DORMANT`（24小时/次）。

### ⚔️ 第 2 轮：特洛伊野生内容与微信封号（Trojan Horse & Account Ban）
* **红方进攻**：全网野生视频充满标题党、阴谋论、血腥恶俗画面或严重政治违规内容。若仅按播放量与点赞数算分，违规视频拿 95 分直冲发布管线，导致微信视频号被永封。
* **蓝方反制**：
  1. **双阶段漏斗防御**：
     - *第一阶（入池门禁）*：时长硬约束（3~30 分钟）；调用 [`censor_engine.check_text()`](file:///Volumes/EXT2T/MacMini4_SSD/PycharmProjects/Video-precessing/src/video_processing/censor_engine.py#L30) 扫描元数据，命中 P0（涉政/暴力）或频道策略一票否决；接入 `gemini-3.7-flash-high` 依据 [`docs/audience_persona.md`](file:///Volumes/EXT2T/MacMini4_SSD/PycharmProjects/Video-precessing/docs/audience_persona.md) 评估受众匹配度（40+ 高净值群体，认可硬核科普，排斥浅薄八卦），$<50$ 分直接淘汰。
     - *第二阶（字幕审查兜底）*：入库加工后，全量中英字幕依然接受 `CensorshipService` 监控，违规即触发 `ACTION_REJECT_SIGTERM` 强杀清理。
  2. **人工审核准入闸门（Human-in-the-Loop）**：野生候选 100% 进入独立待审池，必须在 Web 端人工点击确认后才允许进入加工流水线。

### ⚔️ 第 3 轮：双轨并发主键竞争与脏写死锁（Concurrency & Collision）
* **红方进攻**：白名单频道（如 Harvard）与全网专题搜索同时发现同一期优质视频（`youtube_id` 相同），并发写入导致 SQLite `IntegrityError`，或将正在下载渲染中的任务状态强行覆盖回退。
* **蓝方反制**：
  1. **表级物理读写隔离**：白名单只写 `processed_videos`，专题搜索只写 `topic_candidates`。检索抓取期零目标重叠。
  2. **幂等准入原子事务**：准入时先检查黑名单，再检查 `processed_videos`。若主流水线已存在该视频，保留其原状态（不重置正在进行的切片/下载），仅将 `topic_candidates.state` 更新为 `ADMITTED` 并回填关联 ID。

### ⚔️ 第 4 轮：5,000 行巨石状态机代码腐化（Anti-Spaghetti Defense）
* **红方进攻**：`pipeline_manager.py`（5,084行）和 `database.py`（12,301行）本就体量庞大。若在此处随处增加 `if topic_mode:` 等胶水代码，代码库将彻底失控。
* **蓝方反制**：
  1. **流水线执行器 0 修改**：准入工单被赋予 `source='MANUAL'` 与 `is_manually_scored=1`，走通主流水线原生支持通道。
  2. **独立六边形架构包**：代码全部封装于 `src/video_processing/topic_tracker/`，单向依赖 DAL 与配置中心，不产生逆向与循环依赖。

### ⚔️ 第 5 轮：共享主机量化实盘避让（Host Resource Guard）
* **红方进攻**：本机 Mini 同时承载美股期权实盘交易系统 OptionSense（`backtest`, `batchtest`）。若专题追踪在美股开盘时并发拉取与打分，引起 CPU/网络抖动，导致交易丢包延时。
* **蓝方反制**：
  - 调度器入口强制挂载 [`settings.is_us_market_guard_window()`](file:///Volumes/EXT2T/MacMini4_SSD/PycharmProjects/Video-precessing/src/config/settings.py#L983)。在美股交易时段（美东 09:15–16:15）自动短路暂停关键词探测，确保量化实盘零干扰。

                  └───────────────────────────┘└───────────────────────────┘
```

1. **门面模式（Facade Pattern）— `TopicTrackerService`**  
   对外暴露高内聚方法：`create_topic`、`poll_topic`、`admit_candidate`、`reject_candidate`，封装底层所有过滤器、适配器与配额调用。
2. **适配器模式（Adapter Pattern）— `SearchSourceAdapter`**  
   抽象检索源，支持 `YouTubeDataApiAdapter`、`YtDlpSearchAdapter` 以及完全符合 Mock 门禁（<=3 mocks）的 `MockSearchAdapter`。
3. **责任链模式（Chain of Responsibility）— `CandidateFilterChain`**  
   将野生视频筛选解耦为单一职责节点：去重 $\to$ 时长物理门槛 $\to$ 安全审查 $\to$ 受众调性 AI 门禁。
4. **策略模式（Strategy Pattern）— `TopicAdmissionPolicy`**  
   隔离人工审核与高置信自动准入逻辑，避免条件分支地狱。
5. **令牌桶治理器模式（Governor Pattern）— `QuotaGovernor`**  
   进程安全、跨轮次的 API 预算管控器，防止配额耗尽。

## 5. 数据库与 DAL 演进（零污染设计）

严格执行 DAL 宪法（禁止业务层裸写 SQL），在 [`database.py`](file:///Volumes/EXT2T/MacMini4_SSD/PycharmProjects/Video-precessing/src/video_processing/db/database.py) 的 `_init_db` 中幂等建表：

```sql
-- 1. 专题监控定义表
CREATE TABLE IF NOT EXISTS monitored_topics (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    keyword TEXT NOT NULL UNIQUE,              -- 关键词 (如 "鼠疫", "Blackwell")
    display_name TEXT NOT NULL,                 -- 专题名 (如 "西伯利亚肺鼠疫追踪")
    category TEXT NOT NULL DEFAULT 'HEALTH',    -- MACRO_ECON, TECH, HEALTH, GEOPOLITICS
    status TEXT NOT NULL DEFAULT 'ACTIVE',      -- ACTIVE, PAUSED, EXPIRED
    priority TEXT NOT NULL DEFAULT 'NORMAL',    -- URGENT (4h), NORMAL (12h), DORMANT (24h)
    auto_admit INTEGER NOT NULL DEFAULT 0,     -- 0: 人工复核; 1: 高置信自动放行
    daily_quota INTEGER NOT NULL DEFAULT 3,     -- 每日最大收录条数（防热点刷屏）
    expires_at TIMESTAMP NOT NULL,              -- 热点到期时间 (通常 3~14 天)
    last_polled_at TIMESTAMP DEFAULT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_monitored_topics_status ON monitored_topics(status, priority);

-- 2. 专题候选视频账本表 (与 processed_videos 物理隔离)
CREATE TABLE IF NOT EXISTS topic_candidates (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    topic_id INTEGER NOT NULL REFERENCES monitored_topics(id) ON DELETE CASCADE,
    youtube_id TEXT NOT NULL,
    title TEXT NOT NULL,
    zh_title TEXT DEFAULT NULL,
    channel_id TEXT NOT NULL,
    channel_title TEXT DEFAULT NULL,
    duration_sec INTEGER DEFAULT NULL,
    view_count INTEGER DEFAULT NULL,
    like_count INTEGER DEFAULT NULL,
    upload_date TEXT DEFAULT NULL,
    state TEXT NOT NULL DEFAULT 'PROSPECT'      -- PROSPECT(待审), ADMITTED(已准入), REJECTED(已淘汰), EXPIRED(已过期)
        CHECK(state IN ('PROSPECT', 'ADMITTED', 'REJECTED', 'EXPIRED')),
    relevance_score INTEGER DEFAULT 0,          -- 关键词相关度分 (0-100)
    persona_fit_score INTEGER DEFAULT 0,        -- 受众调性契合分 (0-100)
    audit_reason TEXT DEFAULT NULL,             -- AI 质检评语与审查通过证据
    admitted_video_id INTEGER DEFAULT NULL REFERENCES processed_videos(id) ON DELETE SET NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(topic_id, youtube_id)
);
CREATE INDEX IF NOT EXISTS idx_topic_candidates_state ON topic_candidates(state, persona_fit_score DESC);
CREATE INDEX IF NOT EXISTS idx_topic_candidates_yid ON topic_candidates(youtube_id);
```
