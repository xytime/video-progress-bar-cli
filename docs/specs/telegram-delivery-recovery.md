# Telegram 失败恢复与递增重试

2026-10-18，用户已确认实现范围。实现者：Codex，具体模型身份未知。

## 行为合同

- 英语世界失败通知显示阶段记录中的真实原因，附查看状态、恢复制作、暂停按钮；`/recoveries` 可找回近期恢复卡。已有成片交付请求不得转成生产重做。
- 视频号结果未知时提供后台链接、核验说明及两步人工确认重传。打开后台不代表完成核验。只释放这一条无原生 ID、无受理/历史保护记录的未知项，完整保存原账本与操作者。审核中、已受理和独立英语世界审核链继续阻断通用重传。
- 确认绑定当前成片与发布包 SHA-256，操作时与实际上传前均复核；排队期间文件变化不得静默重传。重复点击、过期按钮、账本变化均拒绝。按钮有效期 24 小时。
- 新上传器在任何发表/草稿点击前同步持久化提交意图。只有同次运行、同一视频、无提交意图且无受理回执的浏览器关闭才能安全自动恢复；其他关闭保留未知状态。
- 封面通知区分生成来源与投稿绑定，生成来源已知不代表平台已收到该封面。

## 重试参数

公共函数 `backoff_seconds`：`max(Retry-After, min(cap, base * 2^(attempt-1)) * U(0.8, 1.0))`。
Retry-After 是调用方传入的最低等待参数；此次未新增 HTTP Retry-After 解析。等待时间、次数写入 SQLite，重启或重复点击不得清零。

| 范围 | 首次等待 | 后续递增 | 上限及预算 |
| --- | --- | --- | --- |
| 具名生产恢复 | 自动安排 4–5 分钟；人工首次恢复可立即排队 | 本轮仍瞬断则 8–10 分钟、16–20 分钟 | 等待上限 1 小时，最多执行 3 次恢复 |
| 有证据的提交前浏览器关闭 | 4–5 分钟 | 8–10 分钟 | 原始上传加最多 2 次恢复；与既有上传恢复共用预算 |
| 协调器当轮瞬断 | 默认 12–15 秒 | 翻倍 | 等待上限 1 小时，沿用当轮次数限制 |
| 失败通知器 / 程序化阶段 / Telegram 建连超时 | 基准 10 / 2 / 1 秒，各自抖动 | 翻倍 | 等待上限 60 / 30 / 30 秒，沿用各自次数限制 |

地区不支持、认证/权限错误、任务预算耗尽不自动循环。未知投稿、读超时、SSL 等有可能已经发送的场景不因退避机制而自动重发。执行者失联超 4 小时转人工核验，禁止自动重放。

## 验收与采用状态

隔离回归覆盖 DAL 原子消费、防重复/过期/陈旧操作、指纹变化、提交意图单调性、受理保护、持久退避、管理员检查、二次确认、内部 API 鉴权、瞬断与永久错误分流。297 项测试及 20 项子测试通过（`video-pytest-jt3ifjcl`）；最终递增区间修正后，12 项恢复专项测试通过（`video-pytest-1ea_vq2m`）。测试结果与来源清单保存在外置盘 TestRuns 回执，不能当作运行采用或真实 Telegram 手机验收。

当前运行采用尚未完成：只读检查发现三个 `ABANDONED_ADMISSION`，对应历史进程已退出；UI/ready-worker 等角色来源与当前源码不匹配，现有已完成部署回执不能匹配当前 UI 来源哈希。没有删锁、伪造来源证明、进入维护、重启现有服务、发送测试消息或重传现有视频。

## 待确认的受控采用范围

这是现有维护来源异常的单独恢复，不修改维护核心或放宽来源校验。

1. 在外置盘保存当前非秘密进程/锁/调度快照、源码清单及 SQLite 一致性备份；再次证明三个历史准入的 PID 已退出且锁无人持有。
2. 准备单列 bootstrap 回执，按现有维护流程暂停领取、等待在途工作结束；只显式回收已证明失主的三条准入，保留原始记录，禁止全目录清锁。
3. 按已核验 PID、启动时间、cwd 受控停止并重新采用 UI、Bot、ready-worker；逐项回读角色来源、健康接口、维护状态和原调度。任何新未知进程、持锁或源漂移均停下，不强杀或伪造证明。
4. 新 DAL 初始化后，仅登记本次英语世界失败实例和 `4hmUTiegBrk` 的当前未知实例，供 `/recoveries` 展示；登记本身不重做、不解除未知、不投稿。
5. 真实 Telegram 回调验收先使用查看/返回动作。生产恢复由明确恢复动作授权；本条视频仅在用户亲自核验后台、再次点击确认后进入既有发布链。平台受理与公开可见分别回读。

首次采用约束见 `docs/specs/deployment-fail-closed-v0.1.md` §4；该步骤不能宣称为原生部署入口的正常路径全流程验收。
