## 目标与原则

把零散异常整理为有证据、可排序、可审核的改进事项，人工批准具体修复方案后实施，并持续检查是否复发。系统可定期分析和提出建议；诊断结论本身不授予修复、重试、发布或放宽质量门禁的权限。

## 推荐首期范围

### 1. 定期分析与报告

每天北京时间 09:00 通过既有入口生成本地日报；每周一同次运行追加周度分析，不另启一套高频巡检。获批后先核实当前调度，确保只存在一个有效入口。每次分析有截止时间、来源、覆盖范围与采集状态；运行重叠时不重复分析。

日报区分三种口径：上一自然日的新增失败事件、截至采样时的未解决存量、近 7 天趋势。历史入库但今天失败的任务必须纳入新增事件；不能只使用现有入库批次 API 代替事件统计。事件账本是计数依据，日志作为佐证。缺日志或旧记录缺事件时显示覆盖不足，不能显示“零异常”。

互斥主分类保持：技术执行故障、流程/依赖阻塞、投递结果待核实、质量/策略拦截、观测不足；正常排队和有效冷却不计技术故障。原片识别不确定可记处理受阻，但在根因确证前不直接断言为代码缺陷。

按任务族和切片分别计数；重试事件数单列。以阶段、结构化原因及脱敏错误特征归并问题，相同异常持续出现更新同一事项，不能每天复制工单。共同根因未确证时仅归为相似症状，保留多个根因的可能。

每日只突出新增、恶化、复发和逾期的重点，默认最多推荐 3 个可行动的改进事项；没有足够证据时不凑建议。周报追踪旧事项和已修复问题的复发情况。

### 2. 一条可审核的改进提案

每条提案必须包含：

- 稳定事项编号、问题范围、首次/最近出现时间、去重任务数、重试事件数和代表性任务链接。
- 事实、根因假设、置信程度、缺失证据；必要时明确下一步仅为调查。
- 推荐修复、涉及模块、预期行为变化、风险、成本、回退办法和不修改的保护条件。
- 可观察的验收任务、回归反例、运行采用证据及观察期指标。
- 方案版本/指纹、批准人、批准时间、批准范围与证据。正文有实质变化时，旧批准不能覆盖新方案。

优先级按实际影响、受影响独立任务、复发频率、持续时长、资源浪费、证据把握及修复成本共同确定；单纯日志行数不能决定优先级。

### 3. 人工审核与执行

流程：发现 → 分析待补证/待审核 → 批准、退回或暂缓 → 实施 → 本地验证 → 运行采用 → 观察 → 关闭或复发重开。

首期在报告和对话中审核，人工批准须绑定具体事项和方案版本，并保存批准证据；报告内容、模型建议及网页文字均不能自行成为批准。批量批准需明确列出事项编号和版本。

批准修复代码不等于批准重试历史任务、批量重置、上传或重新发布。平台结果不确定的任务先核对原生回执；不得自动重发。保留已有审核批准和有效转录、翻译、字幕及成片检查点。

首期不增加后台复杂审批页面，不引入自我修改代码或自动合并机制，不改变字幕、题材与发布门禁。后台现有诊断页面用于查看证据；后续若需统一审核界面，单独确认体验规格。

### 4. 验证改进效果

代码测试通过、主干提交/推送、运行采用、历史任务恢复和外部交付分别记录。

修复后先验证代表性失败及防退化反例，再检查实际运行采用。默认观察 7 天并记录实际执行样本量；没有同类任务运行只能标记“验证通过、效果待观察”，不能自动关闭。确认复发则关联原事项重开。

按同类实际执行任务统计失败率，并分别记录首次成功率、最终加工成功率、恢复耗时、重复调用及资源消耗。供应商尝试失败但任务最终成功不能重复计为任务失败。投递核实积压与质量拦截另行统计，避免通过降低门槛改善表面成功率。

## 实施验收标准

- 同一任务重复失败多次，报告正确呈现一个受影响任务及多个事件；主任务和切片可追溯，不混算。
- 质量/策略拦截、有效等待、技术故障和投递待核实分别展示，任何未知状态不会被当作成功或真实空集。
- 历史入库任务在昨日新发生失败会进入昨日增量；累计数据不冒充当天数据。
- 连续两日报告不复制同一事项；新证据或状态变化能追溯。批准后修改方案会使旧批准失效。
- 分析入口只读取生产事实，输出报告与独立分析/审核记录，不修改视频状态，不启动加工或发布，不发送外部消息。
- 模拟采集失败、报告中断与重复调度时，不清零、不覆盖完整旧报告、不生成重复事项；显示最后有效数据时间和本次错误。
- 修复提案包含具体反例、回退方法和成功指标；关闭记录具备本地验证、运行采用及有样本的观察证据。
- 使用项目隔离测试入口验证上述业务边界；运行、安装调度和报告生成分别给出证据。
