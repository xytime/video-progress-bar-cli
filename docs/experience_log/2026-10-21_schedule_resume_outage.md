## 已核实的故障链

10 月 20 日 17:55 的维护冻结移除了项目 cron，并禁用、卸载了非 UI 的 launchd 作业。后续只恢复了业务维护闸门和 UI。20:35 的部署又把这个冻结现场当作正常基线，最终虽通过“恢复到基线”的校验，日更、封面协调器、通知等周期作业仍未恢复。

UI 自带发现、加工和就绪发布循环仍工作，因此不是全机停机。封面消费停止后，新成片积压在 `AI_COVER_PENDING`，可发布库存耗尽。视频号旧账本仍有已受理但未绑定/未回读的作品，不得把这些作品当作未发布而重传。

恢复中另确认：launchd 拒绝从外置盘私有备份目录加载恢复定义，系统日志明确报告 `bad ownership/permissions`。改用 HOME 本机私有目录后，五项周期作业均已加载、启用；项目 cron 与维护前快照逐字节一致。一次性 forced-recovery 作业保持卸载、禁用，避免重放。

加载状态不等于可执行。后续回读发现 bot 每十秒以 `EX_CONFIG/78` 重启，系统报 `posix_spawn ... EPERM`。分别用系统 shell 和原虚拟环境做无业务启动实验后，证明真正差异是调度器预先打开的外置卷输出日志：原 Python 搭配 HOME 输出日志可以退出 0。最终仅迁移 launchd 的标准输出/错误到 HOME，保留原虚拟环境及业务日志；机器人单实例交接后 PID 55666 已由 launchd 实际拉起。未保留不必要的 shell 包装。
