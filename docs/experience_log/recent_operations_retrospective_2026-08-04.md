# 近期运行问题与解决方案复盘

日期：2026-08-04  
范围：2026-07-25 至 2026-08-04 的 YouTube 到视频号、抖音、快手自动化链路，以及相关的字幕、封面、定时任务和人工配音流程。

## 结论摘要

这段时间的问题并非集中在某一个平台，而是反复出现在四个系统边界：

1. **交互终端环境与 cron 运行环境不同。** 终端可用的 `ffmpeg`、`ffprobe` 或 Node 工具在 cron 最小 `PATH` 下可能不可用；代码在本机测试通过不等于定时任务能运行。
2. **本地状态、提交状态与平台可见状态曾被混淆。** 上传器返回、数据库 `PUBLISHED`、截图、创作者后台作品卡片分别代表不同层级的事实，不能互相替代。
3. **“保护缓存”与“强制重渲”之间缺少故障分类。** 媒体损坏应删除重建，校验工具缺失则必须保留产物；混淆后会把一个环境问题放大为长时间重渲和整队阻塞。
4. **Git 主干已修复不等于生产实例已修复。** 长时间运行的 Python 进程已加载旧模块；提交并 push 后，未重启的实例仍会按旧逻辑继续处理后续任务。

总体上，项目已将大部分“错误发布”的风险收敛为 fail-closed，但“运行版本可见性”和“长任务心跳”仍是最高优先级的可观测性缺口。

## 已沉淀的正确做法

### 1. 先建立证据链，再决定是否重试

发布事故的固定顺序应为：进程与锁 -> 日志 -> 数据库状态 -> 本地产物 -> 提交后证据 -> 创作者后台。  
其中 `PUBLISHED` 仅说明本地流程作出的记录；视频号的 `post_list_after_submission.png` 是提交后证据，而创作者后台作品卡片才可用于确认平台可见。无法确认时保留 `UNDER_REVIEW` 或 `UNCERTAIN`，不自动重发。

这条原则同时防止两类历史问题：把“无高分 AUTO 候选”误判为调度故障，以及把“页面关闭/浏览器异常”误判为发布成功。

### 2. 把 cron 当作独立生产环境测试

cron 不会激活虚拟环境，也通常只带 `/usr/bin:/bin`。以后所有依赖外部命令的修改应满足：

- 命令路径来自 Settings、项目 venv 或受控绝对路径，不依赖交互 shell；
- 同时覆盖父进程校验与子进程执行，不只修某一个 `Popen` 调用；
- 用 `env -i PATH=/usr/bin:/bin` 运行针对性检查；
- 测试覆盖“工具不存在”和“媒体确实损坏”两个分支。

`ffprobe` 事件说明，基础工具本身也是生产依赖；不能把其 `FileNotFoundError` 伪装为业务数据错误。

### 3. 缓存失效必须是保守且可解释的

当前策略应保持如下区分：

| 校验结果 | 处理 |
| --- | --- |
| `ffprobe` 可执行且报告 `moov atom`/时长异常/零时长 | 认定媒体损坏，删除失效派生产物并重渲 |
| `ffprobe` 找不到或校验环境不可用 | 保留成片和字幕，停止当前视频并记录失败原因，待基础环境恢复后精准重试 |
| 双语 ASS 标记缺失 | 认定格式不符合当前合同，重新渲染 |

这使“防止损坏成片发布”与“防止误删可用产物”同时成立，而不是在两者中选一个。

### 4. 让内容和资产的安全门在所有入口一致生效

近期收敛的规则包括：源字幕先行、渲染后字幕复审、发布前复审、专属封面来源/哈希验证，以及配音版本必须使用自己的封面。重点不是增加更多分支，而是让自动发布、历史补录、人工重试和多平台同步共用同一个安全门。

对于封面和普通话译制，文件存在不代表允许提交。必须能证明它是版本匹配的专属生成资产，且不复用原声版或视频帧封面。

## 这次暴露出的不足

### A. 缺少“运行实例版本”这一事实层

08-04 的 `ac5c41e` 已在 `main`，但 04:15 启动的 `run_publication_window.py` 仍保持运行并加载旧代码。日志在 08:59 仍显示旧的 `ffprobe` 缺失后删除缓存行为，说明 Git HEAD 不是该实例的实际代码版本。

**反思：** 过去把“已提交、已 push、测试通过”当成修复完成，这是开发完成，不是生产恢复完成。对长进程而言，还必须验证新 PID、启动时间、加载版本、最小 PATH 和目标任务的实际执行分支。

### B. 锁保证了串行，但没有解释串行进度

每分钟的“上一轮流水线仍在运行，本轮跳过”是正确的互斥行为，但只回答了“为什么没有新任务”，没有回答“旧任务在处理哪条视频、哪个阶段、已经多久、是否仍有进展”。长渲染时这会被用户感知为停止更新。

**反思：** 锁是并发控制，不是可观测性。日志应以阶段心跳和任务上下文补齐锁状态，而不是用高频跳过消息代替进度。

### C. 外部服务错误仍可能进入内容产物

08-04 09:33 的实时日志显示 `LXmCTLSq2Ro` 的渲染标题为 `Error 500`。根因已确认：翻译 fallback 接受了上游 HTTP 错误页，而质量审计未将其识别为无效内容。旧运行在 10:18 因 45 分钟渲染超时停止，未产生视频号提交证据。

**反思：** 对 LLM/HTTP/脚本输出的校验不能只检查“文件存在且非空”，还要拒绝明确的错误页、错误码、占位文本和不满足标题合同的内容。

## 固化的发布判定

以后对“发了吗”“为什么没更新”的回答必须落在以下其中一个可验证状态：

1. 无合格候选：`AUTO + PENDING + score` 不满足当前阈值；
2. 正在处理：给出 PID、视频 ID、阶段、时长和产物变化；
3. 因安全门/基础设施阻断：给出阻断原因和是否保留产物；
4. 已提交待审核：给出不可覆盖的提交后证据；
5. 平台可见：给出创作者后台或平台列表复核；
6. 不确定：明确不重试，并列出还缺少的证据。

任何不属于上述六类的“看起来已经成功”都不应作为对外结论。
