## 结论

这不是“再上传一次”这么简单。发布系统必须同时回答四个彼此独立的问题：

1. 原稿是否真的已删除；
2. 新稿是否明确申请原创；
3. 平台是否受理了这一次新提交；
4. 作品是否已经对公众可见。

本次只确认了前 3 项。新提交使用新的不可变尝试和新的平台原生 ID；不能用旧稿的回执，也不能把 `UNDER_REVIEW` 写成“已公开”。

## 反思

### 1. “审核中”不是“发布成功”

本地 MP4、Telegram 接受、上传器退出码、后台原生 ID、`UNDER_REVIEW`、公众可见，分别是不同层级。以后对外状态统一使用：

```text
LOCAL_PACKAGE -> ORIGINAL_ACTION_CONFIRMED -> PLATFORM_ACCEPTED/UNDER_REVIEW -> PUBLIC
```

只有最后一层才允许表述为“已公开”。

### 2. 删稿后的重投是极窄例外，不是常规重试

默认情况下，已有 `SUBMITTING`、`UNDER_REVIEW`、`UNCERTAIN` 或平台原生 ID 的审核项一律不重传。仅当下列条件同时成立，才允许重投：

1. 用户明确要求；
2. 旧项有精确身份和不可变投稿尝试；
3. 作品管理页形成“旧稿不存在”的可审计证据；
4. 新提交使用新的尝试、新证据目录和新的平台 ID；
5. 旧尝试永远保留，不把新 ID 写回旧记录。

“标题搜索为空”适合辅助确认删除，但不应被伪装成精确 ID 回查成功。后续管理页查询应把这类结果单列为 `TITLE_SEARCH_ZERO`，并要求人工显式绑定到旧原生 ID 后才能进入删除恢复流程。

### 3. 原创声明必须证明平台动作，而不是猜 DOM

第一次恢复时，页面截图已显示橙色选中态，但脚本只依赖一个脆弱的 DOM 读回，导致在未点击发表前安全停止。正确的确认链是：

```text
请求声明原创 -> 弹窗/控件动作完成 -> 提交前后截图 -> 三字段回执 -> 才允许发表
```

这仍然只证明“申请原创动作已完成”，不替代平台后续审核结论。

### 4. 恢复授权必须在数据库中计数，而不是靠文案承诺

此前恢复方法的文档写“尝试一次”，但状态机可在再次失败后重新满足条件，存在无界重复上传风险。现已增加 `original_declaration_recovery_attempts`，原子条件限定为 `= 0`，领取时递增为 `1`。第二次同类失败即使没有平台回执，也不能再领取投稿授权，必须停在失败态供人工诊断。

### 5. 学习质量门禁必须符合屏幕语义

普通阅读屏仍要求至少 8 个微笔记；但最后一屏不适合机械地要求至少 8 条。末屏按可见英文词数使用固定梯度：

| 可见英文词数 | 末屏微笔记数 |
| --- | --- |
| 不超过 12 | 0 |
| 13–24 | 3 |
| 25–40 | 5 |
| 41 及以上 | 8 |

这项规则已经写入日更生产契约；它解决的是“信息密度与画面空间不匹配”，不是放宽普通阅读屏质量。

### 6. 漏发的源头在质量门禁与产物稳定性，不在调度器

本轮两个窗口都实际启动，但分别被“首屏词汇密度不足”和“刚写出的 MP4 尚未完整可解析”拦住；另有来源通路错误曾被错误地当作内容质量问题而永久排除。已形成以下修复：

- 仅明确的内容、屏幕、渲染和音频质量失败才淘汰来源；DNS、Cookie、TLS、403 等通路失败保留来源；
- 渲染先输出同目录临时 MP4，`ffprobe` 验证后原子替换正式文件；
- 最后一屏采用上述 0/3/5/8 梯度，普通屏的 8 条门槛不变。

## 固化后的操作准则

| 场景 | 动作 |
| --- | --- |
| 平台状态未知、后台卡片未加载 | 只读核验，绝不盲目重投。 |
| 已有原生 ID 且用户未明确删稿 | 停止重传，继续精确回查。 |
| 用户明确删除，且管理页有可审计的旧稿不存在证据 | 仅同一审核项、两小时、一次性 `OPERATOR_RECOVERY` 可重投。 |
| 原创声明动作无法确认且未进入发表 | 记录截图和失败回执；仅可恢复一次。二次失败转人工诊断。 |
| 已取得新原生 ID / `UNDER_REVIEW` | 停止提交，后续只读回查。 |
| 公众可见尚未证实 | 明确写“平台受理/审核中”，不得写“已发布”。 |
