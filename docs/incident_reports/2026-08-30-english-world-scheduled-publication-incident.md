## 一、给管理者的结论

用户看到的现象是“昨天下午和今天上午都没有发布”，但底层并不是定时器没有启动。

两次定时任务都按时执行了，只是在后续不同阶段失败：

1. 2026-08-29 16:30：候选视频下载返回 HTTP 403，无法完成画面适龄预检，因旧逻辑过早锁题而无法继续检查下一候选。
2. 2026-08-30 07:00：候选包含剥皮、死禽和明显血迹，且没有可安全截取、严格大于 30 秒、以完整自然句结束的连续片段；同一已淘汰候选之所以再次出现，是因为旧系统只把淘汰原因写在自然语言里，没有形成跨运行的机器排除记录。

事故不是单点故障，而是四个问题叠加：

- 候选锁定时机错误；
- 跨运行淘汰信息不可复用；
- “已排队”和“已执行投稿”的状态语义混淆；
- Telegram、平台受理和公众可见被用户界面表现得过于相似。

主生产与补发链路已经修复并通过全量测试。两个补发作品均已在视频号后台形成唯一原生记录，当前状态为 `UNDER_REVIEW`。这表示平台已经受理，但不能宣称公众端已经公开。

## 三、必须坚持的五层证据模型

这次事故最容易造成误判的地方，是把不同阶段都叫作“成功”。以后所有状态报告必须使用以下五层：

| 层级 | 可接受证据 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 1. 调度执行 | LaunchAgent 运行记录、run log、锁所有者 | 任务确实启动 | 不能证明生成成片 |
| 2. 本地产物 | MP4、manifest、ffprobe、QA、关键帧 | 成片完整且通过本地门禁 | 不能证明 Telegram 收到 |
| 3. Telegram 交付 | Telegram API `ACCEPTED` 与 message_id | 审计/失败消息已被 API 接受 | 不能证明平台提交 |
| 4. 平台受理 | 不可变投稿尝试、原生 post ID、提交后管理页证据 | 平台接受了该次提交 | 不能证明公众可见 |
| 5. 公众可见 | 作品管理页明确已发布、可追溯作品 URL 或公众端读回 | 作品已公开 | — |

任何一层都不得替代下一层。特别是：

- `exit 0` 不等于 Telegram 已交付；
- `SUBMISSION_APPROVED` 不等于已经上传；
- `UNDER_REVIEW` 不等于公开发布；
- 管理页提交截图不等于公众端可见。

## 四、深层根因

### 根因 A：把“选题”误当成一次不可撤销决定

旧系统在字幕或元数据通过后就锁定候选，但真正决定一个视频能否生产的条件还包括：

- 视频格式能否实际下载；
- 画面是否适龄；
- 是否存在严格大于 30 秒、以完整句结束的自然语音；
- 是否没有靠静音、循环或长音乐空档凑时长。

因此，HTTP 403 或画面不适龄本来应该只淘汰当前候选，却被放大成整次窗口失败。

### 根因 B：失败信息只适合人读，不适合机器续跑

`xewivZQgBMQ` 的失败原因写得很清楚，但旧请求没有结构化 `rejected_youtube_ids`。下一次运行不知道它已被淘汰，只能重新下载、重新检查、再次失败。

这说明“日志里写过”不等于“系统记住了”。可参与调度决策的信息必须结构化、可校验、可设 TTL。

### 根因 C：状态名称和退出码掩盖了真实阶段

窗口外自动策略调用投稿器时，旧代码返回 0，并发送“自动投稿执行完毕”，但数据库仍停在 `SUBMISSION_APPROVED`，上传器没有启动。

这是严重的可观测性缺陷：系统没有错误，但运营结论是错的。对发布系统而言，错误的成功比明确失败更危险。

### 根因 D：恢复能力缺少具名、受限、可回收的授权

用户明确要求补发时，旧系统只有两个不理想选择：

- 修改全局发布时间窗口；
- 伪装成 Telegram 人工批准。

两者都会扩大授权范围。正确模型应该是：指定审核号、指定原因、不可变包哈希、零历史尝试、两小时有效、原子领取、过期自动回归普通队列。

### 根因 E：内容代理仍可能生成技术上不单调的字幕时间轴

YouTube json3 自动字幕中的相邻词可能只相差 40ms。若人为设置固定最短词长，前一个词的 `end` 会覆盖下一个词的 `start`。核心模型能拒绝该时间轴，所以没有发布错误成片，但会造成生产窗口失败。

这类约束必须在富化和渲染前验证，而不能依赖渲染阶段碰巧发现。

## 七、建议的日常工作方式

### 每个生产窗口采用“一行五段式”状态

建议每天 07:00、16:30 各形成一条汇总，而不是散落多条含义相近的 Telegram 消息：

```text
07:00｜已执行｜成片 PASS｜Telegram ACCEPTED｜视频号 UNDER_REVIEW｜公众状态待确认
```

发生失败时：

```text
16:30｜已执行｜成片 FAIL：来源下载 403｜失败通知 ACCEPTED｜未调用平台
```

这样用户第一眼就能分辨“没运行”和“运行后失败”。

### 事故处理固定为六步

1. 查调度：是否有本窗口 run log、锁和启动时间。
2. 查产物：是否有 MP4、manifest、实测时长和 QA。
3. 查 Telegram：是否有本次 `delivery.json` 与 message_id。
4. 查投稿账本：状态、尝试数、包哈希、原生 post ID。
5. 决定是否可恢复：只有“明确未提交”才能补发；`SUBMITTING`、`UNDER_REVIEW`、`UNCERTAIN` 一律停止重传。
6. 用五层证据模型汇报，不用“成功/失败”一个词概括全部阶段。

### Telegram 降噪建议

当前成功包会发送前审计、封面、MP4、manifest、结束状态共 5 条消息。建议改为：

- 1 条置顶状态摘要；
- 1 个媒体组承载封面、成片和 manifest；
- 仅在状态发生实质变化时追加一条：`已排队`、`平台受理`、`公开确认`、`明确失败`；
- 相同审核号的重复状态更新编辑原消息，避免另起新消息；
- 失败通知必须包含“是否调用过上传器”，这是判断能否补发的关键字段。

### 建议的服务目标

| 指标 | 建议目标 |
| --- | --- |
| 调度启动 | 计划时间后 5 分钟内有 run record |
| 生产终态 | 启动后 45 分钟内形成 production 或 failure request |
| Telegram 交付 | 请求形成后 5 分钟内得到 ACCEPTED/SUPPRESSED/FAILED |
| 重复投稿 | 同一 artifact hash 和 source ID 为 0 次重复 |
| 状态误报 | `SUBMISSION_APPROVED`、`UNDER_REVIEW` 被写成公开发布的次数为 0 |
| 恢复授权 | 必须具名、单任务、两小时、可审计、过期可回收 |

## 八、建议写入工程宪法的新增条款

以下内容建议作为 `CONTRIBUTING.md` 的新版本，而不是仅留在事故文档中。

### 宪法第二原则：证据层级不可越级

> 调度、产物、消息交付、平台受理、公众可见是五个不同事实。任何状态、退出码、截图或本地账本都不得越级证明下一层。`UNDER_REVIEW` 永远不得表述为已公开。

合并门禁：新增发布流程必须有测试证明每层只接受对应证据。

### 宪法第三原则：恢复必须具名且幂等

> 任何补发、重试、登录恢复或迁移必须绑定明确任务 ID、不可变产物哈希和原始尝试账本。只有确认未提交的技术失败可恢复一次；`SUBMITTING`、`SUBMITTED`、`UNDER_REVIEW`、`UNCERTAIN` 和已有原生平台 ID 均为重传停止态。

合并门禁：新增恢复入口必须有“已有尝试时 uploader 不被调用”的测试。

### 宪法第四原则：候选只有通过完整来源预检后才能锁定

> 元数据或字幕可用不构成选题成功。频道身份、未使用状态、字幕、实际下载、画面适龄、自然语句和时长必须全部通过后才能锁定。锁定前可有界换候选，锁定后不得静默换题。

合并门禁：预检失败必须产生结构化候选 ID 和原因。

### 宪法第五原则：失败也是一等交付结果

> 一个窗口可以以 production 或 failure 结束，但不能无记录结束。失败回执获 Telegram 接受只证明“失败已报告”，不得计入成片交付率或平台发布率。

合并门禁：协调器退出前必须存在可解析的 request 和 receipt，或明确记录 `FAILED_DELIVERY_EVIDENCE`。

### 宪法第六原则：授权必须最小化并自动失效

> 任何窗口外、人工或操作员发布授权必须具名、单任务、短时有效、不可转移，并在未消费过期后自动回到安全队列。禁止通过修改全局窗口、重置通用队列或伪造审批来源完成单条恢复。

合并门禁：必须测试过期、重复签发、进程中断和并发领取。

### 宪法第七原则：状态消息必须面向运营决策

> 禁止使用“执行完毕”“发布成功”等模糊词。消息必须明确回答：任务是否启动、是否有成片、Telegram 是否接受、上传器是否调用、平台是否受理、公众是否可见。

合并门禁：状态枚举与用户文案必须一一映射，不能由退出码 0 推导业务成功。

### 宪法第八原则：代码上线必须有运行态版本证明

> Git commit、测试通过和 push 都不证明定时任务已经加载新代码。每个常驻或计划入口必须记录实际运行 revision、启动时间和终态，并由健康检查读回。

合并门禁：涉及调度器的修改必须同时验证安装态、下一次实际运行 revision 和工作区分支。

### 宪法第九原则：多平台发布必须独立记账

> 视频号、抖音及未来平台必须分别记录 READY、SUBMITTING、UNDER_REVIEW、PUBLISHED、UNCERTAIN 和失败证据。一个平台的受理或公开状态不得代替另一个平台的状态。

建议实现方式：同一已审核 artifact 可以进入多个平台独立任务，但每个平台必须复核实际标题、文案、封面和字幕；禁止通过复制视频号本地状态来宣称抖音已发布。

- 在窗口前做只读 Cookie 与来源可用性探针，不提前生产、不触发平台；
- 统计“窗口执行率、成片率、Telegram 交付率、平台受理率、公众确认率”，禁止合并成一个成功率；
- 对外部平台回查抖动采用退避式只读验证，不以回查失败触发重传。

## 十、最终判断

本次事故的主生产、通知和一次性恢复问题已经解决，且不是靠放宽安全门禁解决。系统现在能更准确地区分：

- 没有运行；
- 运行后没有成片；
- 成片已交付 Telegram；
- 平台已受理；
- 公众已经可见。

仍需明确保留两个边界：

1. 视频号最终公开状态由平台审核决定，当前只能确认 `UNDER_REVIEW`；
2. 英语世界尚未建立经过验证的抖音独立发布闭环，不能把“以后也发布到其他平台”视为已经完成。

这两个边界不应通过盲目重传或模糊文案消除，而应分别通过只读平台回查和独立多平台账本解决。
