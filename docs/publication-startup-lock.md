# 巡航启动前防重入

2026-09-22，Codex。

## 故障与边界

巡航原有 `publication_window_runner.lock` 在依赖导入及英语世界回查之后才获取。
主机严重拥堵时，Python 初始化和依赖导入本身可停留数小时，每分钟 cron 因此
不断生成尚未抵达业务锁的实例。现场曾积压 51 个无子任务、无处理锁的巡航进程；
日志另有 `database is locked`。这不等于 51 次投稿，也不证明所有整机负载来自本项目。

## 修复

受管 cron 在 Python 解释器前执行 macOS `/usr/bin/lockf -ks -t 0`，使用独立的
`output/publication_window_startup.lock`，覆盖解释器启动、导入、回查和完整巡航。

- `-t 0`：已有实例时立即退出，不排队、不启动 Python。
- `-k`：保留同一个锁文件，避免删除再创建产生不同 inode 的并发漏洞。
- `-s`：锁忙不刷日志；锁忙退出码为 75，实际子任务退出码保持原值。
- 原有业务锁、平台去重、审查和暂停策略全部保留；不重置任何候选或已受理状态。
- 锁由系统管理，文件存在不代表仍被持锁；不要删除锁文件来“解锁”。

代码安装入口为 `scripts/install_publication_window_schedule.sh`；校验器要求受管区块
恰有一条带启动锁的本项目巡航命令，并拒绝本项目重复入口。
本次线上仅精确替换原来的一条 cron 命令，其余条目原样保留，未运行旧安装器的广域清理。

## 验证与限制

隔离测试直接使用安装器命令模板，实测忙锁时不启动解释器、子任务全生命周期持锁、
退出后可重入、锁文件保留、子任务错误码透传，以及计划校验。
此次同时固定旧日志裁剪测试的时钟，避免日期变化造成假失败。

此锁只保护受管巡航，不改变其他项目或其他入口；主机资源不足仍可能使唯一实例很慢。
运行采用须以 `lsof output/publication_window_startup.lock` 和 cron/进程回读确认，
内容交付须另查发布账本与平台状态，不得把测试通过或进程数减少当作公开发布。
